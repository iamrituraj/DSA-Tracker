01

What Kafka Is

Kafka is an open-source, distributed event streaming platform used to collect, process, store, and route massive volumes of real-time data. Originally built at LinkedIn, now an Apache Software Foundation project — it handles trillions of messages daily for streaming analytics, data integration, and mission-critical applications.

Key capabilities

High throughputMillions of messages/second with minimal latency (as low as 2 ms)
Fault tolerancePartition logs replicated across multiple brokers to prevent data loss
Durable storagePersists streams to disk; retains data by time/size policy — not deleted on consumption
EcosystemBuilt-in stream-processing APIs + hundreds of connectors (Confluent & OSS community)

Kafka vs a traditional broker (RabbitMQ)

ModelAppend-only commit log vs AMQP queue
After consumeKafka retains data by time/size — multiple consumers can re-read history; RabbitMQ deletes on ack
ScalingKafka scales horizontally via partitioning; RabbitMQ focuses on complex routing rules
ReplayKafka can rewind offsets and replay; a queue gives the message back only on nack

Framing for the interview: Kafka is not a queue — it is a distributed, ordered, append-only log database. Almost every "weird" Kafka property (ordering only per-partition, no message priority, consumers pull instead of push, replayability) falls out of that single sentence.

Core Architecture

Four roles, one data structure. Producers publish, Brokers store, Consumers pull sequentially by offset — and everything lives in topics split across partitions.

producer traffic partition leader consumer traffic replication (leader → follower)

The four pillars

ProducersApplications/services that create and publish messages (events) to Kafka
BrokersIndividual servers forming the cluster; store data and service client requests
TopicsNamed categories/feeds where records are stored
ConsumersServices subscribing to topics, reading data sequentially via managed offsets

Why partitions exist

ParallelismA topic is split across brokers so multiple consumers in one group read simultaneously
ScalabilityThe core unit of scale — a single log file would cap throughput at one disk/node
OrderingOrder is guaranteed within a partition; a key pins related events to the same partition
ReplicationEach partition is replicated (1 leader + N followers) for fault tolerance
03

Log-Centric File System

Kafka's throughput does not come from clever in-memory caching — it comes from how it uses the host OS's disk and memory layers. This is the production-grade answer to "why is Kafka fast?".

Log segments

A partition is not one giant file. It is a logical directory on the broker's disk containing a series of log segments (typically 1 GB files, configured by log.segment.bytes).

# orders-topic / partition 0 on disk
logs/orders-topic-0/
  00000000000000000000.log        # segment: append-only data
  00000000000000000000.index      # offset → physical file position
  00000000000000000000.timeindex  # timestamp → offset
  00000000000001572864.log        # next segment (name = base offset)
  ...
PropertyWhy it matters
Append-only writesThe disk head performs sequential I/O — bypassing random-seek latency. On modern disks, sequential writes can match or exceed the speed of random memory access.
Sparse index files.index maps offsets to file positions and .timeindex handles time lookups, so a consumer fetch at offset N is a binary search + one seek — not a scan.
Immutable recordsNothing is ever rewritten in place — which is also why a broker can serve huge read volumes without lock contention.

Zero-copy network transfer (sendfile())

A traditional app copies bytes four times per read. Kafka eliminates the middle copies using the Linux kernel sendfile() system call:

traditional:  [ Disk ] → [ Page Cache ] → [ User App Buffer ] → [ Socket Buffer ] → [ NIC ]

kafka:        [ Disk ] ──► [ Page Cache ] ──────────────────────► [ NIC Buffer ] ──► consumer socket
                                ▲ Kafka bridges this directly (zero-copy)

Data goes straight from OS page cache to the NIC buffer. The JVM never touches the bytes — no context switches into user space, no GC pressure on streamed data. This is the second half of the reason the JVM heap can stay tiny (see §14).

04

Partitions In Depth

Partitions are defined at the topic level when the topic is created — they cannot be varied per message. With N partitions, Kafka numbers them 0 … N-1, and each maps to an actual directory of append-only log segments on the hosting broker's file system.

Defining partitions (creation)

# CLI — 6 logical partitions (0 through 5); RF 2 = 1 leader + 1 follower copy per partition
kafka-topics.sh --bootstrap-server localhost:9092 --create \
  --topic analytics-topic \
  --partitions 6 \
  --replication-factor 2
// C# (.NET AdminClient) — same topic, programmatically
using var adminClient = new AdminClientBuilder(new AdminClientConfig { BootstrapServers = "localhost:9092" }).Build();

await adminClient.CreateTopicsAsync(new TopicSpecification[] {
    new TopicSpecification { Name = "analytics-topic", NumPartitions = 6, ReplicationFactor = 2 }
});

Scaling partitions later — and the hashing trap

You can increase the partition count dynamically. You cannot decrease it — deleting a log segment would cause irreversible data loss.

# Increase partitions: 6 → 12
kafka-topics.sh --bootstrap-server localhost:9092 --alter \
  --topic analytics-topic \
  --partitions 12

The key-hashing trap gotcha

Kafka's default partition formula is Partition = MurmurHash2(Key) % TotalPartitions. If a producer relies on a key (e.g. User_123) to keep a user's events on one partition for ordering, changing TotalPartitions from 6 to 12 re-maps the same key to a different partition — past and future events for that entity scatter across partitions and per-key ordering breaks. Choose partition counts up front, or plan a dual-write migration when scaling.

How a message picks its partition

CaseBehavior
A · Explicit partitioningProducer manually overrides the logic and names the target partition (e.g. "send to partition 3") — bypasses all hashing
B · Keyed messagesKafka hashes the key and mods against the active partition count — guarantees strict ordering for that key
C · Null keyModern Kafka uses a Sticky Partitioner: pick a partition, pack records into its batch until the batch fills or a timeout hits, then "stick" to another partition — optimizes network batching and evens out broker load (old round-robin alternated per record and defeated batching)

Rule of thumb — how many partitions?

Partitions = max( TargetThroughput / ProducerSpeed , TargetThroughput / ConsumerSpeed )

Example: one consumer thread processes 10 MB/s, requirement is 60 MB/s
→ define ≥ 6 partitions and run 6 parallel consumer instances in the group

Consumer speed is usually the binding constraint — a single consumer can read many partitions fast, so the practical floor is often set by consumer parallelism, not producer throughput.

Python producer & consumer

# ---------- producer: publish JSON events to test-topic ----------
import json, time
from kafka import KafkaProducer

producer = KafkaProducer(
    bootstrap_servers=['localhost:9092'],
    value_serializer=lambda v: json.dumps(v).encode('utf-8')
)

for i in range(1, 6):
    data = {'message_id': i, 'timestamp': time.time(),
            'status': 'Active', 'payload': f'Hello Kafka message number {i}'}
    producer.send('test-topic', value=data)
    print(f"Sent: {data}")
    time.sleep(1)

producer.flush()   # block until all buffered records are delivered
producer.close()
# ---------- consumer: poll and print as records arrive ----------
import json
from kafka import KafkaConsumer

consumer = KafkaConsumer(
    'test-topic',
    bootstrap_servers=['localhost:9092'],
    auto_offset_reset='earliest',
    enable_auto_commit=True,
    value_deserializer=lambda x: json.loads(x.decode('utf-8'))
)

try:
    for message in consumer:
        print(f"Received from Partition {message.partition} at Offset {message.offset}")
        print(f"Content: {message.value}")
except KeyboardInterrupt:
    print("Stopping consumer...")
finally:
    consumer.close()

Multi-topic + keyed producer (C#)

Topics separate business domains (orders-topic vs billing-topic); a string key (e.g. user ID) pins each entity's messages to one partition. One consumer instance can subscribe to several topics — Kafka balances all their partitions across the group.

using var producer = new ProducerBuilder<string, string>(config).Build();  // Key AND Value are strings

string[] topics = { "orders-topic", "notifications-topic" };

for (int i = 1; i <= 6; i++)
{
    string selectedTopic = topics[i % 2];
    // same key → same partition, always → strict per-entity ordering
    string key   = i % 2 == 0 ? "user_A" : "user_B";
    string value = $"{{\"id\": {i}, \"data\": \"Payload for {key}\"}}";

    var report = await producer.ProduceAsync(selectedTopic,
        new Message<string, string> { Key = key, Value = value });

    Console.WriteLine($"[Sent] Topic: {report.Topic} | Key: {report.Key} → Partition: {report.Partition} | Offset: {report.Offset}");
    await Task.Delay(500);
}
// ---------- consumer subscribing to multiple topics ----------
using var consumer = new ConsumerBuilder<string, string>(config).Build();

var topicsToListen = new List<string> { "orders-topic", "notifications-topic" };
consumer.Subscribe(topicsToListen);  // partitions auto-balanced across group members

while (!cts.Token.IsCancellationRequested)
{
    var r = consumer.Consume(cts.Token);
    Console.WriteLine($"[Received] Topic: {r.Topic} | Partition: {r.Partition} | Key: {r.Message.Key} | Value: {r.Message.Value}");
}

Producer internals — what happens after Produce()

                     ▼                        ▼
              selects partition        batches by topic-partition
1

Partitioner

MurmurHash2(Key) % PartitionCount. Null key → sticky partitioner: pack records into one partition's batch until full, then rotate to balance broker load.

In-memory micro-batching by topic-partition; holds records up to batch.size (default 16 KB) per batch.

Consumer Groups & Rebalancing

Multiple instances of a consumer form a consumer group — Kafka splits the topic's partitions among the active members. Rule to memorize: each partition is assigned to exactly one consumer within a group, which is what prevents duplicate processing across instances of the same service.

The group-coordination protocol

1

Group Coordinator

One broker in the cluster is designated the coordinator for your group.

2

Heartbeats

Every consumer instance sends background heartbeats (typically every 3 s) to the coordinator — "I am alive." Missing them past session.timeout.ms declares the instance dead.

3

Rebalance triggers

A consumer crashes (heartbeat stops), joins or leaves the group, or takes longer on one batch than max.poll.interval.ms — the coordinator declares it dead and triggers a rebalance.

4

Partition reassignment

The coordinator takes the dead consumer's partitions and reassigns them to the remaining healthy consumers.

5

Resume via offsets

The newly assigned consumer asks: "What was the last committed offset for this partition?" — fetches it from __consumer_offsets and continues exactly where the predecessor left off.

Mitigating frequent rebalances

Lever Move it how / why
max.poll.recordsTune down so one batch always finishes inside max.poll.interval.ms
Processing loopOptimize per-record work; never do unbounded external calls inside the loop
session.timeout.msBalance false-positive death detection vs real failover speed
AssignorUse Cooperative Sticky Assignors to avoid "stop-the-world" rebalances — partitions are migrated incrementally instead of revoking everything first

The rebalance problem without EOS: Instance A reads a message, processes it into the DB, and crashes before committing. Rebalance moves the partition to Instance B, which re-reads from the last committed offset and processes the same message again — that is at-least-once, and it's by design (§07).

Offsets & Commit Semantics

An offset commit is how a consumer tells the cluster which messages it has successfully read and processed. Kafka stores offsets in an internal, replicated system topic: __consumer_offsets. Because positions are tracked, a crashed/restarted/rebalanced consumer resumes precisely where it left off — no reprocessing old data, no skipping.

The three positions you must distinguish

partition log:   ──[0]──[1]──[2]──[3]──[4]──[5]──[6]──(empty)──
                  ▲                ▲                ▲
            committed offset   current offset      LEO
            (saved in          (next record the    (one past the last
             __consumer_        consumer reads      record written
             offsets)           on next poll)       by producers)
OffsetDefinition
Current offsetPosition of the next record the consumer loop is about to read on the next Consume()/poll()
Committed offsetLast pointer saved in __consumer_offsets — where a restarting consumer looks up and begins fetching
Log End Offset (LEO)Position of the absolute last message written to the partition by producers

Auto-commit risky

EnableAutoCommit = true (the default). Every Consume() call checks whether AutoCommitIntervalMs (default 5000 ms) has passed; if so, a background thread fires an async commit of the latest fetched offset.

+Zero management code
−Pull a batch → auto-commits → crash while processing → those messages are lost (Kafka thinks they were completed). Or the reverse window yields duplicates.

Manual commit production

EnableAutoCommit = false — you trigger commits in code, giving exact control over delivery guarantees.

Commit(r)Synchronous: halt until the broker acknowledges the offset is saved. Highly reliable, adds per-commit network latency.
StoreOffset(r)Asynchronous: store locally, fire an unblocked request. High throughput; a crash right after may roll back slightly on restart.

Delivery guarantees are decided by when you commit

GuaranteeOffset committedIf the consumer crashes…
At-most-onceBefore processing (as soon as Consume() hands you the message)You risk losing data — the message is skipped on reboot because Kafka thinks it was processed
At-least-once standardAfter business logic / DB write succeedsYou risk duplicates — next consumer re-reads the uncommitted message and runs it again → downstream must be idempotent
Exactly-once (EOS)Via Kafka transactions — output production + offset commit in one atomic blockNo loss, no duplicates — both succeed or both fail together (§08)

C# — manual at-least-once commit

var config = new ConsumerConfig
{
    BootstrapServers = "localhost:9092",
    GroupId = "orders-processor-group",
    EnableAutoCommit = false,              // 1. turn off background tracking
    AutoOffsetReset = AutoOffsetReset.Earliest
};

using var consumer = new ConsumerBuilder<string, string>(config).Build();
consumer.Subscribe("orders-topic");

while (!cts.Token.IsCancellationRequested)
{
    var result = consumer.Consume(cts.Token);

    ProcessOrderInDatabase(result.Message.Value);  // 2. business logic FIRST

    consumer.Commit(result);  // 3. commit only AFTER the work succeeds (blocking, ack'd)
}
08

Exactly-Once Semantics (EOS)

EOS = idempotent producer (no duplicate writes on retry) + transactional processing (consume → transform → produce → commit-offset as one indivisible atomic block). Either everything succeeds, or everything rolls back.

Mechanism 1 — idempotent producer

A producer initialized with idempotency receives a unique Producer ID (PID) from the cluster and attaches a monotonically increasing sequence number to every message, per topic-partition.

1

Send

Broker receives the record and writes it to disk…

2

ACK lost

…but the network drops before the ACK returns. Producer retries.

3

Dedupe

Broker compares the incoming sequence number against its log for that PID. Already committed? Drop the duplicate but return success. No double write.

Mechanism 2 — transaction coordinator & 2PC

Multi-topic transactional loops route through a dedicated broker role, the Transaction Coordinator:

1

Init + fencing

Producer registers its unique TransactionalId; the coordinator increments an epoch number, instantly fencing out any older "zombie" instance of that producer.

2

Tracking

As the producer writes to topics and sends consumer offsets, the coordinator logs the involved partitions in an internal transaction-status log.

3

Phase 1 — Prepare

CommitTransaction() → coordinator writes a PREPARE_COMMIT token to its log.

4

Phase 2 — Commit markers

Coordinator writes a physical control message — a commit marker — to every partition involved in the transaction.

5

Downstream read

Consumers with isolation.level=read_committed buffer records and emit them to your loop only on encountering the commit marker. An ABORT marker → buffered messages are cleanly dropped.

The EOS workflow (consume → transform → produce, atomically)

1. BeginTransaction()
2. Consume a message from the input topic
3. Process it; write the result to an output topic with a TRANSACTIONAL producer
4. SendOffsetsToTransaction()      // the offset joins the transaction instead of a normal commit
5. CommitTransaction()             // data + offset become visible (or roll back) together

C# — working EOS pipeline

string inputTopic = "orders-topic", outputTopic = "analytics-topic";

// 1. Transactional producer — TransactionalId MUST be unique & persistent per app instance
var producerConfig = new ProducerConfig
{
    BootstrapServers = bootstrapServers,
    TransactionalId = "eos-producer-id-1",
    EnableIdempotence = true              // implicit when TransactionalId is set
};

// 2. Consumer — no auto-commit: offsets are committed INSIDE the transaction
var consumerConfig = new ConsumerConfig
{
    BootstrapServers = bootstrapServers,
    GroupId = "eos-processor-group",
    EnableAutoCommit = false,
    AutoOffsetReset = AutoOffsetReset.Earliest
};

using var producer = new ProducerBuilder<string, string>(producerConfig).Build();
using var consumer = new ConsumerBuilder<string, string>(consumerConfig).Build();

producer.InitTransactions(TimeSpan.FromSeconds(10));  // fences out zombie instances on the broker
consumer.Subscribe(inputTopic);

while (!cts.Token.IsCancellationRequested)
{
    var r = consumer.Consume(cts.Token);
    if (r == null) continue;

    producer.BeginTransaction();
    try
    {
        string processed = r.Message.Value.ToUpper();   // business logic

        // A. produce the output INSIDE the transaction
        producer.Produce(outputTopic,
            new Message<string, string> { Key = r.Message.Key, Value = processed });

        // B. attach the consumed offset to the transaction — committed only if it succeeds
        producer.SendOffsetsToTransaction(
            new[] { new TopicPartitionOffset(r.TopicPartition, r.Offset + 1) },
            consumer.ConsumerGroupMetadata,
            TimeSpan.FromSeconds(10));

        // C. commit everything simultaneously — data + offset, atomically
        producer.CommitTransaction();
    }
    catch (KafkaException ex)
    {
        Console.WriteLine($"Transaction error: {ex.Message}. Rolling back...");
        producer.AbortTransaction();   // nothing published, offset not committed → re-read later
    }
}

Downstream isolation is not optional: readers of analytics-topic only see EOS benefits if they filter aborted/uncommitted records:

var downstreamConfig = new ConsumerConfig
{
    BootstrapServers = "localhost:9092",
    GroupId = "dashboard-group",
    IsolationLevel = IsolationLevel.ReadCommitted  // skip records of aborted/uncommitted transactions
};

Replication, ISR & the Durability Triad

Replication is Kafka's mechanism for fault tolerance and data durability. Kafka runs on clusters of commodity servers, so individual hardware failures are expected — a broker can physically die and the messages must still be safe and available elsewhere.

Leaders and followers

Replication is defined by a Replication Factor (RF) at the topic level. RF = 3 → three distinct copies of every partition, spread across different brokers:

                ┌──────────────────────────────────────┐
                │             KAFKA CLUSTER            │
                │                                      │
  PRODUCER ────►│  [ Broker 1 ]      [ Broker 2 ]      │────► CONSUMER
 (writes to lead)│  Partition 0       Partition 0       │  (reads from lead)
                │   (LEADER)          (FOLLOWER)       │
                └───────┬──────────────────▲───────────┘
                        │                  │
                        └─(replication)────┘
Leader replicaOne broker elected per partition — all read and write traffic from clients goes to the leader
Follower replicasBackground consumers — accept no client writes; continuously poll the leader and copy new log entries to their own disks

In-Sync Replicas (ISR)

Not every follower is byte-for-byte current at any given millisecond (network lag). Kafka tracks a dynamic subset — the ISR list:

RuleDetail
MembershipA follower is "in-sync" if it mirrors the leader's log within replica.lag.time.max.ms (usually 10 s)
EjectionBroker crash, bad network, or disk I/O bottleneck → follower falls behind → dropped from the ISR → partition is under-replicated (metric: UnderReplicatedPartitions)
CRITICALOnly brokers currently in the ISR are eligible for election as the new leader when the leader fails — never a lagging replica, or committed data would vanish

The triad of durability (production best practice)

1 · replication.factor = 3

Always 3 in production — survive loss of up to 2 brokers without losing access. Never 1.

2 · min.insync.replicas = 2

Topic/cluster safeguard: "reject writes unless leader + ≥1 healthy follower are in the ISR." ISR shrinks to 1 after two brokers crash → writes rejected with NotEnoughReplicas — data integrity over availability.

3 · acks = all

Producer blocks until the leader and every current ISR member have written the record to disk.

acksWaits forTrade-off
0Nothing — fire and forgetMax speed; total data-loss risk on broker death
1Partition leader onlyBalanced; leader crash before replication loses the record
all (-1)Leader + all ISRsMaximum durability; higher latency per write

Broker failure, step by step

1

Detection

The KRaft controller instantly notices the missing heartbeat from the broker holding the partition leader.

2

Election

It consults the partition's ISR list and elects a healthy follower as the new leader.

3

Rerouting

Producers automatically refresh cluster metadata and seamlessly route traffic to the new leader — zero application downtime.

Rack awareness (broker.rack): map brokers to AZ/rack identifiers so Kafka spreads a partition's replica set across failure domains instead of stacking all three copies on hardware that fails together.

Priority Messages (Emulated)

Kafka has no native message priority. RabbitMQ can scan and reorder a queue; Kafka is a strictly append-only, immutable log — repositioning a message would break its core design guarantees. Prioritization must be built into the system architecture with one of three patterns.

Strategy 1 — Multi-topic isolation recommended

                ┌───► [ high-priority-topic ] ───► Dedicated Consumer Group (More Nodes)
                │
PRODUCER ───────┼───► [ medium-priority-topic ] ──► Standard Consumer Group
                │
                └───► [ low-priority-topic ] ────► Batch / Background Consumer Group
MechanicsProducer inspects a payload attribute (e.g. tier="VIP") and routes to the matching topic
Consumer isolationIndependent consumer fleets: high-priority group gets more instances/compute to minimize latency; low-priority chews through backlog cheaply
Why it winsPredictable; eliminates noisy-neighbor problems entirely; per-tier lag metrics are trivial to monitor

Strategy 2 — Single-consumer priority polling

// pseudo-logic inside the execution loop — one fleet, sequential drains
while (true) {
    // 1. drain HIGH first
    var msg = consumer.PollFromTopic("high-priority-topic", timeout: 100);
    if (msg != null) { Process(msg); continue; }

    // 2. if empty, check MEDIUM
    msg = consumer.PollFromTopic("medium-priority-topic", timeout: 100);
    if (msg != null) { Process(msg); continue; }

    // 3. fall back to LOW
    msg = consumer.PollFromTopic("low-priority-topic", timeout: 100);
    if (msg != null) { Process(msg); }
}

Starvation risk hazard

A burst of high-priority events means the loop never drops to low priority — background work stalls indefinitely. Combat with a weighted round-robin (e.g. read 3 high records per 1 low record) instead of strict drain-first.

Strategy 3 — Bucket priority (single topic, partition ranges)

Forced onto one topic? Split priority classes by partition ranges: a 10-partition topic with a custom producer partitioner sending partitions 0–5 = high, 6–8 = medium, 9 = low; a custom consumer worker pool assigns more workers to the high-priority range.

Cost: over-complicates Kafka's default cluster rebalancing and breaks standard message-key sorting across partitions.

PatternComplexityStarvation riskBest for
Multi-topicLow (standard Kafka)NoneEnterprise multi-tenant apps; premium vs free tiers
Priority pollingMedium (custom loop)High (needs tuning)Single service handling intermittent critical alerts
Bucket patternHigh (custom partitioner)MediumSystems locked into one strict topic

Retention, Compaction & Tiered Storage

Kafka does not delete messages when a consumer reads them. Cleanup follows per-topic rules — the two policies plus the modern storage extension.

Time / size retention

Delete data older than a threshold (log.retention.hours=168 → 7 days) or once the partition directory exceeds a size cap (e.g. 50 GB). Whole segments are dropped, never individual records — keeping sequential-I/O discipline on the delete path too.

Log compaction

cleanup.policy=compact — instead of deleting old data, Kafka scans the log and removes duplicate older keys, keeping only the latest value for each key. Ideal for rebuilding application state / database snapshots from the log without it growing forever. (This is exactly how __consumer_offsets itself stays bounded.)

Tiered storage (modern Kafka)

TierContentsHardware
Local tierAbsolute latest data (e.g. last 24 h)Fast local NVMe/SSD — low-latency consumer access
Remote tierOlder historical log segments, shipped automaticallyCheap, infinitely scalable object storage (S3 / Azure Blob) — still readable seamlessly at a fraction of the cost

Historically, long retention meant buying expensive SSDs for every broker; tiering decouples retention length from local disk size.

12

Ecosystem: Streams, Schema Registry, DLQ

Beyond the raw producer/consumer clients, four ecosystem pieces round out the architectural knowledge a Kafka interview probes.

Stream processing

Kafka StreamsLightweight Java/.NET library for complex operations on live data: stream-to-stream joins, aggregation (real-time averages), and windowing (count events over rolling 5-minute windows)
ksqlDBEvent-streaming database — express continuous stream transformations as plain SQL queries instead of code

Schema governance

Objects evolve; a producer silently changing a JSON payload can crash every downstream consumer. The Confluent Schema Registry + binary formats (Avro / Protobuf) acts as a central governance gateway: before publishing, the client checks the payload against predefined compatibility rules (e.g. no deleting fields old consumers still depend on).

Dead letter queues (DLQ)

A malformed/corrupt message — a poison pill — halts the processing loop; ignoring it blocks the entire partition forever. Pattern: the error catch intercepts the bad message, writes it to a separate topic (orders-dlq) for manual inspection, then commits the original offset so the primary pipeline keeps flowing.

Connectors

Hundreds of out-of-the-box connectors (via Confluent and the OSS community) for databases, cloud storage, and stream systems — the "data integration" face of the platform, on top of the same log.

KRaft — the Metadata Control Plane

KRaft (Kafka Raft metadata mode) replaces ZooKeeper by running the consensus protocol directly inside Kafka brokers. Metadata management is now fully internal: simpler architecture, no external metadata-sync lag, clusters scale to millions of partitions with near-instantaneous controller failover.

       ┌─────────── KRaft Controller Quorum (3 Nodes) ───────────┐
       │                                                         │
       │   [ Controller 1 ] ◄──► [ Controller 2 ] ◄──► [ Leader ] │
       └───────────────────────────┬─────────────────────────────┘
                                   │ (metadata log replication)
                                   ▼
                  ┌──────────── Active Data Brokers ────────────┐
                  │ [ Broker 1 ]   [ Broker 2 ]   [ Broker 3 ]  │
                  └─────────────────────────────────────────────┘
1

The quorum

An odd number of controllers (3 or 5) run a Raft-based consensus protocol to elect a single Active Controller Leader. Odd sizing survives split-brain faults in metadata consensus.

2

The metadata log

All cluster configuration, topic definitions, and partition assignments live in an internal metadata topic: @metadata.

3

State propagation — push, not pull

Data brokers don't fetch metadata on demand; they actively replicate the @metadata stream. When a partition leader dies, the Active Controller writes the new state to the log and every broker learns the topology shift in milliseconds — no routing bottleneck.

16

Interview Playbook

The question bank, grouped the way interviewers do — fundamentals, deep dive on commits/rebalancing, then senior-level EOS and scaling.

Core architecture & fundamentals junior/mid

What is Apache Kafka, and how does it differ from a traditional broker like RabbitMQ?
A distributed event streaming platform built on an append-only log, vs RabbitMQ's AMQP queue model. Kafka retains data after consumption by time/size policy so multiple consumers can re-read history; RabbitMQ deletes on ack. Kafka scales horizontally via partitioning; RabbitMQ focuses on complex routing.
What is a partition and why does it matter?
An ordered, immutable sequence of records continually appended to — a commit log. Partitions are the core unit of scalability and parallelism: they split one topic across multiple brokers so multiple consumers in a group can read from it simultaneously.
What is the purpose of a consumer group?
It acts as a single logical consumer for scalable, parallel processing: Kafka assigns each partition to exactly one consumer instance within the group, preventing duplicate processing across instances of the same service.
What does auto.offset.reset do?
Defines behavior when there is no committed offset, or the committed offset no longer exists on the server: earliest starts from the beginning of the log; latest reads only messages arriving after the consumer boots.

Commits, rebalances & delivery mid/senior

Auto-commit vs manual commit — the risks of each?
Auto commits the last fetched offset on a timer (default 5 s) — blind, so a crash mid-processing loses those messages. Manual (enable.auto.commit=false) puts the developer in control: commit after processing guarantees at-least-once, but a crash before committing replays duplicates.
What triggers a rebalance, and how do you mitigate frequent rebalances?
A consumer joins/leaves, or misses heartbeats within session.timeout.ms, or a batch takes longer than max.poll.interval.ms. Mitigate: optimize the processing loop, tune max.poll.records down, use Cooperative Sticky assignors to avoid stop-the-world rebalances.
How does Kafka guarantee message ordering?
Only within a single partition — never across a topic. Related events (same user ID) must be pinned to one partition with a consistent message Key that hashes to that partition.

Advanced: EOS & production scaling senior/lead

How does Kafka achieve exactly-once semantics?
Idempotent producers (PID + per-partition sequence numbers deduplicate retried writes) plus transactional processing: the consume-transform-produce loop wraps outgoing messages and the consumer's offset commit in one atomic transaction. Downstream consumers must use isolation.level=read_committed.
What is KRaft and how does it replace ZooKeeper?
Raft consensus running inside Kafka itself over an internal @metadata log. Eliminates the external coordination service and its metadata-sync lag; scales to millions of partitions with near-instant controller failover.
Role of acks? Trade-offs of acks=all?
How many replicas must acknowledge before the send counts as successful: 0 (fire-and-forget, loss risk), 1 (leader only), all/-1 (leader + every ISR member). all = maximum durability at the cost of write latency.
What are ISRs, and when does a partition become under-replicated?
Followers still mirroring the leader within replica.lag.time.max.ms. A follower falls behind (network, disk bottleneck) or its broker crashes → it drops out of the ISR → the partition is under-replicated; that metric is your #1 cluster alarm.
Why can't you decrease partition count? What breaks when you increase it?
Decreasing would delete log segments — irreversible data loss. Increasing changes hash(key) % totalPartitions, so existing keys re-map to new partitions and per-key ordering scatters. Plan counts up front; scale via migration, not in-place alteration.
Does Kafka support message priority?
No — the log is strictly append-only; repositioning records breaks its guarantees. Emulate with multi-topic priority tiers (recommended), a priority-polling consumer loop (starvation risk → weighted round-robin), or partition-range buckets (custom partitioner, fights rebalancing).
Why is Kafka fast? Give the systems answer.
Sequential append-only disk I/O (beats random access), OS page cache instead of JVM heap (heap capped at 6–8 GB by design), zero-copy sendfile() from page cache to NIC so the JVM never touches bytes, client-side batching (batch.size/linger.ms) with pre-transport compression, and sparse offset/time indexes for O(log n) fetch positioning.
