01

Core Problem & End-to-End Architecture

Goal: given an order that just got accepted by a restaurant, find the rider who will arrive soonest — not just nearest in a straight line — while tens of thousands of riders stream location updates concurrently. The diagram separates the write path (constant location ingestion) from the read path (matching, triggered per order) because they have very different load shapes and failure tolerances.

write path read path lock / mutation durable buffer background / async
Kafka sits between the stateless WS gateway and the ingestion worker so a burst of GPS pings never becomes a direct write storm on Redis — the worker consumes at its own pace, and a worker restart doesn't lose in-flight pings.
1

Stream

Riders push GPS over a persistent WebSocket roughly every 3 seconds. The gateway tier is stateless and horizontally scaled behind a load balancer — it only authenticates the connection and forwards the ping.

2

Buffer

Pings land on a Kafka topic partitioned by coarse region (the res-5 hex, say), not by rider ID. This gives ingestion workers a durable, replayable queue and decouples gateway throughput spikes from Redis write throughput.

3

Bucket

The Ingestion Worker converts each (lat, lng) into an H3 index at resolution 8 (~740m across) and moves the rider between hex sets: SREM old hex, SADD new hex, update the status hash — ideally as one Lua script for atomicity.

4

Trigger

An order transitions to "ready for pickup." The Matching Engine resolves the restaurant's own H3 index at the same resolution.

5

Expand & rank

k-ring expansion gathers candidates via SUNION, a cheap haversine pre-filter shortlists the closest few, and only those go to OSRM for real road-network ETA.

6

Lock & notify

The winning rider is claimed atomically with SET rider_lock:<id> NX PX 15000, then pushed a notification. Accept flips their status — which re-enters the write path — or the lock expires and the next candidate is tried.

03

Geohash vs. Uber H3

The whole design hinges on picking a geo-index whose neighbors behave predictably. This is the single most interview-worthy tradeoff in the system.

Geohash — square grid

Redis-native (GEOADD/GEORADIUS), but a square's diagonal neighbor is √2× farther than its cardinal neighbor. A ring search either over- or under-reaches depending on direction, and cell size distorts with latitude because it's a lat/lng-derived grid, not a true equal-area one.

Uber H3 — hexagonal grid

Application-layer index (a library call, not a Redis feature). Every one of the 6 neighbors sits at the same distance from center, so a k-ring expansion is a mathematically uniform, evenly-growing search radius — no directional distortion.

ResolutionEdge lengthUsed for
5~8.5 kmShard anchor / city-level hash-tag grouping
7~1.2 kmCoarse hot-spot / surge-zone aggregation
8~460 m edge (~740m diameter)Rider ingest bucket — the working resolution
9~175 mToo fine for ingest — churns riders between cells on every ping

One caveat worth raising unprompted: H3 hexagons aren't perfectly uniform either — 12 unavoidable pentagons exist where the icosahedron folds (near icosahedron vertices, mostly over oceans). Global logistics platforms note it but it essentially never touches dense urban delivery zones, so it's a "know it exists" fact, not a design blocker.

04

Redis Data Model & Sharding

Redis Cluster refuses multi-key operations that span shards — a SUNION across two hex sets on different nodes throws CROSSSLOT. Hash tags are the fix.

Only the text inside { } is hashed for slot placement — every child hex and every rider under one res-5 parent lands on the same physical node.

Why this specific pair of resolutions

Res-8 (~740m) is fine enough that a k-ring of 2–3 rings covers a realistic pickup radius without pulling in irrelevant riders. Res-5 (~20km) is coarse enough that one parent hex safely contains an entire metro's worth of res-8 children — so a citywide k-ring search never needs to cross a hash-tag boundary, keeping SUNION and the locking Lua script single-shard and network-hop-free.

05

Matching Engine: k-ring Expansion

Straight-line H3 distance is a cheap pre-filter. Only the surviving shortlist is worth the expensive routing-service call.

-- pseudocode, run inside the Matching Engine
function findRider(order):
  originHex = h3.fromLatLng(order.restaurant.lat, order.restaurant.lng, RES_8)
  candidates = []
  k = 0
  while candidates.size < MIN_CANDIDATES and k <= MAX_K:
    ring = h3.kRing(originHex, k)          -- hexes at exactly/within ring k
    ids  = redis.SUNION(ring.map(hexKey))  -- single shard, no cross-hop
    candidates += fetchStatus(ids).filter(isAvailable)
    k += 1

  shortlist = candidates
    .sortBy(haversineDistance)
    .take(TOP_N)                            -- cheap pre-filter, e.g. top 8

  ranked = shortlist.map(r => osrm.eta(r, order.restaurant))
                     .sortBy(eta)

  for rider in ranked:
    if redis.SET("rider_lock:" + rider.id, order.id, NX, PX 15000):
      return offer(rider, order)   -- push notification, wait for accept
  return NO_RIDER_AVAILABLE

Why pre-filter by straight-line distance before calling OSRM: routing calls are the expensive step (network hop + graph search on the routing service). Running OSRM against every rider in a wide k-ring wastes latency budget on riders that were never going to win. Haversine on H3 centers is O(1) and gets the shortlist down to the handful worth a real ETA.

Complexity to state out loud: a k-ring at level k covers 3k² + 3k + 1 hexagons (1, 7, 19, 37…). SUNION over m sets of average size n is O(m·n) — with m capped by MAX_K and n bounded by rider density, this stays sub-linear in the total rider count, which is the whole point versus scanning every online rider.

Consistency Model & Failure Modes

Different pieces of this system deliberately sit at different points on the consistency spectrum — naming that explicitly is what separates an SDE-2 answer from an SDE-1 one.

ComponentConsistencyWhy that's the right choice
Rider location (hex sets)EventualA rider's position is stale by definition the moment it's read — being off by one ping (~3s of travel) is a non-issue for a ~740m bucket.
Offer lockStrong (linearizable)Correctness bug, not a UX nit, if two orders both think they claimed the same rider — this is exactly what SET NX's atomicity buys.
Order state machineStrongOwned by a transactional store (Postgres, not Redis) — an order must never be visible as both "ready" and "assigned" simultaneously to two workers.
Redis replica reads (if used for scale)EventualFine for candidate gathering (a slightly stale rider set just means one extra OSRM call gets wasted); never read the offer lock from a replica.

Failure modes and how the design degrades

Kafka partition unavailableOne region's rider pingsGateway buffers briefly / backpressures the WS connection; riders' last known position just ages a bit — acceptable for a location feed
OSRM instance slow/downMatching latency onlyFall back to straight-line-distance ranking with a wider safety margin, or route to a secondary OSRM replica; never block the whole match on it
Ingestion worker crashesDelayed hex updates for its partitionKafka consumer group rebalances to a healthy worker; no data loss since offsets aren't committed until the Redis write succeeds
07

Production Edge Cases

These are the two edge cases interviewers push on hardest — have the mitigation and its own failure mode ready.

Ghost Riders STALE DATA

A rider's app crashes, loses signal, or their phone dies — no clean disconnect event fires, so their ID stays sitting in the hex set forever, occasionally winning matches for a rider who was never there.

MitigationBackground cron scans rider:status:* hashes; any with last_updated older than ~15–20s (5–6 missed pings) gets SREM'd from its hex set and marked offline.
Residual riskCron interval creates a window where a ghost can still be matched — mitigated further by re-validating last_updated at offer time, right before the lock, not just at candidate-gathering time.
Scale noteA single sweeping cron becomes a bottleneck past a few hundred thousand riders — shard the sweep by hash-tag prefix so each shard's reaper only scans its own keys, running in parallel.

Double Booking RACE CONDITION

Two orders in overlapping hexes both shortlist the same nearby rider in the same few hundred milliseconds — without coordination, both could offer the order to them simultaneously.

MitigationSET rider_lock:<id> <order_id> NX PX 15000
Why NX mattersNX makes the write conditional on the key not already existing — atomic in Redis, so exactly one of the two concurrent matching processes wins the lock; the other falls through to its next-best candidate.
Why PX 15000Bounds how long a rider can sit "reserved" without responding. If they don't accept/reject in 15s, the key expires and they become matchable again automatically — no manual cleanup needed.
Release-on-accept nuanceOn explicit accept/reject, delete the lock immediately rather than waiting out the TTL — use a Lua script that checks the value equals the expected order_id before deleting, so a late duplicate accept can't delete a newer lock (classic check-then-delete race).

Alternatives Considered

Naming what you didn't pick, and why, shows the tradeoff reasoning interviewers are actually grading.

AlternativeRejected because
PostGIS / PostgreSQL geospatial indexStrong consistency and rich querying, but ~100K small writes/sec with single-digit-ms latency is a poor fit for a disk-backed relational store under constant index churn from moving points.
Elasticsearch geo-queriesGreat for complex, infrequently-changing geo search (store locators), but its indexing latency doesn't suit a value that changes every 3 seconds per document at this volume.
Redis native GEO (GEOADD/GEORADIUS)Simpler — no external H3 library — but built on the same square-grid distortion as Geohash; ring/radius correctness suffers exactly where it matters most: mid-density urban cores.
Client-side polling (riders pull nearby orders)Inverts the push model; every rider polling every few seconds for "any orders near me" multiplies read load by rider count instead of concentrating cost at match time.
In-memory app-server cache instead of RedisWorks at one-instance scale, but with N matching engine instances behind a load balancer, rider location would need to be replicated to every instance — Redis centralizes it once instead.
09

Interview Playbook

Likely follow-ups once you've walked through the base design, with the shape of a strong SDE-2-level answer.

Downtown hot-spot overloads a single shard (e.g. Friday night, one res-5 parent hex) — what breaks and how do you fix it?
The hash-tag design that keeps things fast for normal load becomes the bottleneck: one parent hex means one shard absorbs all read/write traffic for that whole metro. Fixes to discuss: (1) split hot parents into multiple hash-tag shards by adding a sub-shard suffix derived from a hash of the child hex, trading some cross-shard SUNION cost for load spread; (2) cache read-heavy hot zones (surge multiplier, availability counts) in a local in-memory layer refreshed every second instead of hitting Redis per request; (3) apply write-side backpressure — batch rider pings for a hot zone instead of one write per ping per rider.
A Redis shard crashes mid-match — what's the recovery flow?
Redis Cluster promotes a replica automatically (assuming replicas are configured), so the shard-level state (hex sets, status hashes) survives with sub-second failover, but in-flight commands during the failover window can be lost. The Matching Engine should treat any Redis error during k-ring expansion as retryable with a short backoff, and any in-flight offer lock as unconfirmed until it reads back a success — never assume a write succeeded on a timeout. Idempotency matters here: retried matching for the same order should be safe to run twice.
Why not just use Redis GEO commands instead of H3?
GEOADD/GEORADIUS is geohash-backed under the hood, so it inherits the same square-grid distortion. H3 is chosen specifically for uniform ring expansion and because hexagon adjacency is a solved, well-tested library (used at Uber's actual scale) rather than something to reinvent on top of Redis GEO.
How do you pick resolution 8 specifically, and how would you defend that number?
It's a tradeoff between churn and search cost. Too fine (res 9, ~175m) and riders flip between cells on almost every ping, generating unnecessary SREM/SADD pairs. Too coarse (res 7, ~1.2km) and a single hex can hold far more riders than are actually reachable, forcing more OSRM calls than necessary. Res 8 (~740m) roughly matches a typical dense-urban pickup radius, so a k=1 or k=2 ring usually already has enough candidates.
How would you extend this to handle rider preference / fairness, not just nearest-ETA?
Pure nearest-ETA optimizes the current order but can starve riders at the edge of a zone over a shift. A common extension: weight ranking by a fairness score (e.g. time since a rider's last delivery, or a rolling earnings target) alongside ETA, or reserve a small percentage of offers for a round-robin pass. Flag the tension explicitly — it's a product tradeoff (customer wait time vs. rider fairness), not a purely technical one, and worth saying so.
How do you test/validate this without a live fleet of riders?
Replay recorded GPS traces through the ingestion path in a staging Redis cluster to validate bucket transitions; property-test the locking Lua script directly for the concurrent-claim race (spin up N goroutines/threads hammering the same rider_lock key and assert exactly one succeeds); load-test the matching path with synthetic hex distributions matching real density (dense downtown vs. sparse suburb) to catch k-ring performance cliffs before they hit production.
