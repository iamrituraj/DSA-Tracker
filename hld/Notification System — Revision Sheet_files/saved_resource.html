Worth flagging explicitly: "at-least-once" is a deliberate choice, not a default — it means duplicates are possible and the client/vendor side needs to tolerate or dedupe them. Exactly-once delivery across a network boundary to a third-party vendor is not achievable without the vendor's cooperation (idempotency keys on their end), so don't over-promise it.

02

End-to-End Architecture

Same separation-of-concerns principle as any high-throughput system: keep the synchronous API thin, push everything slow or bursty onto a queue, and make workers stateless so they scale horizontally.

sync request path async dispatch failure / retry vendor call
The API only validates, dedupes, and enqueues — it never waits on a third-party vendor. Everything vendor-latency-sensitive lives in the async dispatch path so a slow SMS provider can't back up push or email.
1

Accept

Notification API validates the request, assigns a notification_id, and returns immediately — it never blocks on delivery.

2

Dedupe & gate

Redis idempotency key (user_id + event_type + timestamp_minute) drops duplicate triggers; the preference service checks the user hasn't opted out of this category/channel.

3

Render

Template service fetches the localized template by template_id and substitutes runtime variables, with a cache in front since templates change far less often than they're read.

4

Enqueue

Message lands on Kafka, split by priority (high: OTP/security vs. low: marketing) and by channel (push/SMS/email topics), decoupling API latency from provider latency entirely.

5

Dispatch

Stateless channel workers pull from their topic and call the vendor. A Strategy-pattern abstraction lets a worker fail over from, say, Twilio to AWS SNS on a 5xx without any caller-side change.

6

Retry or park

Failures go to a backoff retry queue (2s → 8s → 32s); after N attempts, the message moves to a dead-letter queue that pages someone instead of silently vanishing.

Partition/cluster this by (notification_id, ts) — write-heavy, rarely updated, and the access pattern is almost always "all events for one notification" or "all events in a time window," which a wide-column store handles far better than a relational table with a hot index.

Device token management, briefly: mobile clients rotate their FCM/APNs tokens periodically — store them keyed by user_id, and when a push provider responds Unregistered / BadDeviceToken, mark that token inactive asynchronously rather than failing the whole dispatch. This is a small detail interviewers specifically listen for, since it's the kind of production wrinkle a spec-only design misses.

05

Reliability & Delivery Guarantees

At-least-once is the target — the interesting part is defending exactly where the "at least" comes from and what it costs.

MechanismWhat it guarantees
Kafka offset commit only after vendor confirmsA crashed worker mid-dispatch never loses the message — it's redelivered to another consumer on rebalance
Retry with exponential backoffTransient vendor errors (5xx, timeout) don't become permanent failures
Dead-letter queue after N retriesPermanent failures (bad token, invalid number) are surfaced for inspection instead of retried forever
Idempotency key at ingestionClient-side retries of the *request* don't fan out into duplicate sends

Idempotency key design, one level deeper

Key shape: dedup:{user_id}:{event_type}:{minute_bucket}, written with SET key notification_id NX EX 90. The minute-bucket granularity is a deliberate tradeoff — coarse enough to catch a retry storm (a client hammering "resend OTP" in a tight loop), fine enough not to suppress two legitimately distinct events of the same type in the same minute (two separate orders confirmed 10 seconds apart). If the business needs per-event rather than per-minute dedup, the caller should supply its own idempotency key (e.g. order_id) instead of relying on the time bucket.

The tradeoff to name: "commit offset only after vendor confirms" trades throughput for safety — the consumer can't move on to the next message on that partition until the current one is acked (or the worker parallelizes within a partition and tracks acks separately, which adds complexity). This is exactly why partition count and consumer parallelism become the throughput knob, not single-consumer speed.

06

Scaling to Millions per Second

The baseline design handles thousands/sec comfortably. The interesting follow-up — almost guaranteed in an SDE-2 round — is "now do it for a flash sale to 5 million users."

The fan-out problem

A single broadcast trigger ("sale starts now") must not become 5 million synchronous API calls — that crashes the gateway before a single notification goes out.

FixAPI accepts one broadcast_id + target_segment_id; a dedicated fan-out worker pages through matching users in batches (e.g. 50K at a time) from a fast read store and publishes individual dispatch tasks onto Kafka — the fan-out happens inside the system, not at the API boundary.
Where reads come fromA high-throughput read replica or wide-column store (Cassandra/ScyllaDB) built for exactly this kind of segment scan, not the primary transactional DB.

Kafka partitioning & consumer scaling

Partition key = hash(user_id) — one user's events always land on the same partition (preserving per-user order), while total load spreads evenly across up to 64+ partitions. Each partition is owned by exactly one consumer in the group at a time, so partition count is the hard ceiling on dispatch parallelism.

08

Vendor Connection & Rate-Limit Management

Third-party providers are the ceiling on this system's real-world throughput, not your own infrastructure — this is the section most candidates skip and most interviewers care about.

·

Connection pooling

Persistent HTTP/2 connections to APNs/FCM avoid a TLS handshake per notification — the difference between milliseconds and tens of milliseconds per call at volume.

·

Token-bucket throttling per provider

Each worker pool enforces its own vendor's documented rate limit locally, so a burst never trips the vendor's own rate limiter and risks account suspension.

·

Provider fallback (Strategy pattern)

A common interface (send(notification)) with Twilio and AWS SNS both implementing it — a 5xx or timeout from the primary triggers an automatic swap, invisible to the rest of the pipeline.

Worth saying explicitly: "DELIVERED" status for push/SMS often relies on the vendor's own delivery webhook, not just a successful API call — a 200 from FCM means "accepted for delivery," not "landed on the device." A complete design distinguishes SENT (we handed it to the vendor) from DELIVERED (the vendor confirms receipt), and treats only the latter as the real success metric where the vendor supports it.

Security & Compliance

A system that sends messages to real phone numbers and inboxes has obligations beyond throughput — this section is a quick way to show breadth without derailing the core design.

Security

API authService-to-service auth (mTLS or signed JWT) — this is an internal API called by other services, not end users directly
Vendor secretsAPI keys/certs in a secrets manager (Vault/KMS), never in worker config or source
PII in transitTLS everywhere; template data (order amounts, addresses) never logged in plaintext at the info level
Webhook verificationVendor delivery-status webhooks (bounce, click, delivered) must be signature-verified — an unverified webhook is a spoofable status-update vector

Compliance

UnsubscribeEvery marketing email needs a working one-click unsubscribe (CAN-SPAM); honoring it must be near-immediate, not eventually-consistent over hours
Quiet hours / TCPASMS to US numbers has time-of-day and consent restrictions — enforce at the preference-check step, not left to the vendor
Data retentionDelivery logs containing PII need a retention policy and deletion path (GDPR "right to erasure") — ties directly into the TTL/compression story from capacity planning
Audit trailWho/what triggered a notification (service, admin action) should be traceable from the delivery log, not just the outcome

Multi-Region & Disaster Recovery

A transactional notification path (OTPs, password resets) can't go dark because one region's data center has a bad day.

Active-passive by default: one region takes live traffic, the other stays warm via cross-region replication (Kafka MirrorMaker, DB replica). DNS/global load balancer failover redirects traffic on region-health failure. Active-active is possible but adds real complexity — cross-region dedup keys, conflict resolution on preference writes — worth mentioning as the next step, not the starting point.
FailureRecovery
One region fully downGlobal LB fails traffic over to standby region; Kafka consumer groups in the new active region pick up from the last mirrored offset
Cross-region replication lagA brief window where a just-changed preference (e.g. new opt-out) might not yet be visible in the standby — acceptable for this workload's consistency model, flagged explicitly rather than hidden
Split-brain risk if active-activeOnly relevant if you extend beyond active-passive — requires a conflict-resolution strategy on preference writes (e.g. last-write-wins with vector clocks), worth naming as a known cost of that upgrade

Alternatives Considered

AlternativeRejected because
Synchronous send in the API requestTies API latency to the slowest vendor of the moment; one degraded provider takes down the whole notification path
Single Kafka topic for all channels/prioritiesA marketing backlog would delay OTP delivery — priority and channel separation exists specifically to prevent that

Interview Playbook

A vendor (say, Twilio) goes down entirely for an hour — what happens?
The Strategy-pattern abstraction fails over to AWS SNS automatically on repeated 5xx/timeout from Twilio. If both are degraded, messages accumulate in the retry queue with backoff rather than being dropped; the dead-letter queue and an alert catch anything that exceeds the retry budget so a human is paged instead of silently losing OTPs for an hour.
How do you guarantee ordering, and do you even need to?
Kafka guarantees order only within a partition, so partitioning by hash(user_id) keeps one user's notifications in order relative to each other, which is usually the only ordering guarantee that matters (a user shouldn't see "delivered" before "order confirmed"). Cross-user ordering is never required, which is exactly what makes horizontal partitioning safe here.
How would you prevent a marketing broadcast from starving transactional notifications?
Separate topics per priority, separate consumer groups sized differently (more workers on the high-priority topic), and if using a single shared worker pool, weighted polling that always drains high-priority before low-priority. The design already splits high/low priority topics for exactly this reason — worth calling that out proactively rather than waiting to be asked.
How do you avoid re-notifying a user who already unsubscribed mid-flight?
Check preferences at enqueue time (before Kafka) and again at dispatch time (right before the vendor call) — a user could opt out in the seconds between a marketing broadcast being fanned out and a given worker actually processing their message. The second check is cheap (single key lookup) relative to the cost of an unwanted send and the compliance risk it carries.
How would you test this without hitting real vendor APIs?
Mock vendor adapters behind the same Strategy interface used in production, so a test send exercises the real dispatch/retry/DLQ logic against a fake that can be told to fail on command. Load-test the fan-out path separately with synthetic segment sizes to find the batch-read bottleneck before it shows up in a real flash sale.
How do you know the delivery-success number on the dashboard is actually trustworthy?
Distinguish SENT (accepted by vendor's API) from DELIVERED (vendor's own webhook confirms receipt on-device/inbox) in the data model, and compute the headline metric from DELIVERED where the vendor supports webhooks, falling back to SENT with that caveat stated where it doesn't (SMS delivery receipts, for instance, are less universally reliable than push).
If this needs to run in two regions for compliance (EU data residency) as well as DR, what changes?
Data residency is stricter than DR — EU user data and its delivery logs must stay in-region, not just be replicated there as a warm standby. That pushes toward per-region partitioning of the user base itself (a user's preferences and logs live only in their home region) rather than the simpler active-passive replication used for pure availability, and it's worth naming that distinction explicitly since interviewers sometimes probe whether a candidate conflates the two.
