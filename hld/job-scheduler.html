The tension to name up front: jobs are accessed two conflicting ways — by time (the scheduler asking "what's due now") and by identity (a user asking "what's the status of my job"). Almost every hard decision in this design — sharding key, index shape, storage tiering — exists to serve both access patterns without one degrading the other.

02

End-to-End Architecture

Three concerns, decoupled so each scales independently: submission (API path, write-heavy but simple), scheduling (time coordination, the hard part), and execution (resource management, embarrassingly parallel).

submission path scheduling / time layer execution path async / background
The metadata DB is the durable source of truth; Redis is a disposable, rebuildable cache of "what's due soon." Losing the Redis layer is an availability blip, not a data-loss event — that distinction is worth stating explicitly in an interview.
1

Submit

Job Service validates the payload (cron syntax, command reference) and writes it to the sharded metadata DB — this write must succeed before the API returns, since durability is a hard requirement.

2

Surface

A CDC stream (or periodic sweeper) moves jobs due within the next lookahead window from cold storage into a Redis sorted set, scored by their next trigger timestamp.

3

Coordinate

Scheduler nodes load the imminent slice of that ZSET into an in-memory timing wheel and step through it once per second, claiming a distributed lease before dispatching each due job.

4

Buffer

Claimed jobs are published to a message broker — this protects the worker pool from a burst of simultaneously-due jobs and lets workers consume at their own sustainable pace.

5

Execute

Stateless workers pull tasks, run them, and write results/logs to a write-optimized store (Cassandra/S3), updating the execution's status in the metadata DB.

ColumnType

Why two tables, not one: a recurring cron job has exactly one definition but potentially thousands of executions over its lifetime. Splitting them means updating a schedule (pause, change cron expression) touches one small row, while the high-volume write traffic (每次 execution's status transitions) lands in a separate table that can be partitioned and purged independently — this separation is what makes the partitioning strategy in section 07 possible at all.

04

Timing Wheel & Distributed Lease

The two mechanisms that make "trigger within 1–2 seconds" possible without hammering a database every second.

Timing wheel — a circular array of time buckets

Each bucket = one second, holding the job_ids due at that instant. The pointer sweeps one bucket per second; when it lands on a bucket, every job listed there fires — O(1) per tick instead of a scan, regardless of how many total jobs exist in the wheel.

Distributed lease — preventing duplicate dispatch

Multiple scheduler nodes tick the same wheel concurrently (for availability) — without coordination, two nodes could both see the same due job and dispatch it twice.

-- Redis lease, atomic claim before dispatch
SET lease:{execution_id} {scheduler_node_id} NX PX 5000

-- or, if staying pure-SQL (see section 05):
SELECT ... FOR UPDATE SKIP LOCKED

Whichever node wins the lease dispatches; every other node simply skips that execution_id for this tick. The short TTL means a node that dies mid-claim doesn't block the job forever — another node's next tick picks it up.

05

Querying Due Jobs — Two Patterns

Naive WHERE scheduled_time <= NOW() polling degrades as rows grow into the billions. Two production patterns solve it very differently.

Pattern 1 — CDC + Redis Sorted Set

DB only ever handles inserts and cold storage. Scheduler never touches it during polling. Eventually consistent — Redis can lag the DB by milliseconds.

Pattern 2 — SQL SKIP LOCKED

CREATE INDEX idx_pending
  ON job_executions (status, scheduled_time)
  WHERE status = 'PENDING';

BEGIN;
SELECT execution_id FROM job_executions
WHERE status = 'PENDING'
  AND scheduled_time <= NOW()
ORDER BY scheduled_time
LIMIT 100
FOR UPDATE SKIP LOCKED;
-- Node B's identical query skips
-- rows Node A already locked
COMMIT;
FeatureCDC + Redis ZSETSQL SKIP LOCKED
DB loadExtremely lowMedium–high, constant polling
Max scaleMillions of jobs/minTens of thousands/min
ComplexityHigher — Redis + CDC infraVery low — pure SQL
ConsistencyEventual (ms-level lag)Strict ACID

How to pick between them out loud: start with SKIP LOCKED — it's simpler and genuinely fine until tens of thousands of jobs/min. Name Redis+CDC as the upgrade path once that ceiling is hit, rather than reaching for the more complex pattern first. Interviewers notice when a candidate over-engineers the starting point.

06

Sharding Strategy

Jobs are read two conflicting ways — by time (scheduler) and by identity (user dashboard). Shard purely by either one and the other pattern breaks.

Shard purely by...What breaks
scheduled_timeHot shard — every write and read concentrates on whichever node owns "right now"; every other node sits idle
user_idFan-out problem — the scheduler must broadcast "what's due" to every shard instead of one

The resolution: shard by tenant, decouple the time-read path

Primary shards are keyed by tenant_id (consistent hashing) — this keeps a user's dashboard query, cancellations, and schedule edits confined to one shard, and eliminates cross-shard transactions for user-facing actions. The scheduler's time-based read never touches these shards directly: CDC streams new/updated jobs into the globally-accessible Redis ZSET (pattern 1 above), so "what's due now" is answered from one hot, purpose-built index instead of fanning out across every tenant shard.

Hot tenant edge case

One enterprise tenant triggering millions of jobs/minute can overwhelm its single assigned shard even though every other tenant is fine.

MitigationTwo-tier sharding — once a tenant's throughput crosses a threshold, sub-shard their own data using hash(tenant_id, job_id), spreading just that tenant's load across multiple nodes while everyone else stays on simple single-shard routing.
07

Table Partitioning Inside a Shard

Sharding spreads load across machines. Partitioning solves a different problem: one shard still holding hundreds of millions of rows in a single flat table.

A query constrained by scheduled_time gets pruned by the planner to touch only p2026_09_22 — the other partitions' data and indexes are never read from disk.
CREATE TABLE job_executions (
  execution_id UUID NOT NULL,
  tenant_id VARCHAR(64) NOT NULL,
  scheduled_time TIMESTAMP NOT NULL,
  status VARCHAR(20) NOT NULL,
  PRIMARY KEY (tenant_id, scheduled_time, execution_id)
) PARTITION BY RANGE (scheduled_time);

CREATE TABLE job_executions_2026_09_22 PARTITION OF job_executions
  FOR VALUES FROM ('2026-09-22 00:00:00') TO ('2026-09-23 00:00:00');
WinWhy
Index localizationActive partition's micro-index fits entirely in RAM instead of a billion-row B-tree thrashing disk
Partition pruningA time-bounded query touches one sub-table; the planner skips every other month/week entirely
Zero-overhead purgingDROP TABLE p2026_08_15

Operational gotcha: pre-allocation

A write for a future date fails outright if that date's partition table doesn't exist yet — partitions aren't created lazily on first write. A scheduled background job (cron/Kubernetes CronJob) must pre-create the next day's/week's partitions well ahead of time, and a filtered partial index (WHERE status='PENDING') on each partition keeps lookups fast even as completed rows accumulate within the same day.

08

Tiered Storage for Far-Future Jobs

A job scheduled for next month has no business sitting in an in-memory hot layer today — that's pure RAM waste at billions-of-jobs scale.

Same idea as an OS memory hierarchy — pay for RAM only for the sliver of data actually about to be used. A next-month job sits frozen on disk, in its own future-dated partition, costing nothing until its window approaches.

Two ways this stays correct automatically: under the CDC+Redis pattern, an hourly/daily sweeper explicitly promotes jobs into the warm buffer as their window nears. Under the pure SQL SKIP LOCKED pattern, nothing needs to actively "promote" anything — partition pruning already means the query planner ignores October's partition table entirely while it's still September, so cold data is invisible to the hot path for free, as a side effect of the partitioning scheme in section 07 rather than a separate mechanism.

09

Fault Tolerance & Edge Cases

Worker crashes mid-job VISIBILITY TIMEOUT

A worker pulls a task and dies before finishing — the task must not simply vanish.

MitigationThe broker's visibility timeout expires without an ack, so the message rolls back onto the queue automatically for another worker — this is exactly what satisfies "at-least-once."
Residual riskA job that isn't idempotent can run twice with real side effects (e.g. double-charging) — the design guarantees at-least-once dispatch, not exactly-once side effects; the job itself needs to be idempotent if that matters.

Scheduler node crashes VOLATILE STATE

The timing wheel lives in memory — a crash could silently drop everything it had pre-cached.

MitigationThe wheel is rebuilt from a durable source on restart — either a write-ahead log of recent claims or simply re-reading the next window from Redis/DB, since the wheel is a cache, not the source of truth.

Repeated task failure RETRY EXHAUSTION

MitigationExponential backoff on retry; after a fixed threshold (e.g. 5 attempts) the task routes to a dead-letter queue for manual inspection instead of retrying forever and masking a real bug.

Interview Playbook

How do you handle a job whose execution takes longer than the tick interval?
The scheduler's job is dispatch, not execution — once it hands a task to the broker and a worker picks it up, the scheduler's involvement ends. A long-running job is a worker/visibility-timeout concern (make the timeout comfortably longer than the expected max runtime, or have the worker send periodic heartbeats to extend it) rather than something that blocks the next tick of the wheel.
Two scheduler nodes both think they own the same due job — walk through exactly what stops a duplicate dispatch.
Both nodes' ticks land on the same wheel bucket and both attempt to claim the lease (SET lease:{id} NX PX 5000 or SELECT ... FOR UPDATE SKIP LOCKED). Only one SET NX can succeed — Redis serializes it. The loser doesn't retry that execution this tick; it moves on. This is the same atomic-claim pattern as an offer lock in a matching system — worth drawing that parallel if it's come up earlier in the interview.
How would you support job dependencies (run B only after A succeeds) without a full DAG engine?
A lightweight version: job B's row carries a depends_on: job_id field and status WAITING instead of PENDING; a worker completing A publishes a completion event that flips B to PENDING. This avoids building full DAG orchestration (Airflow-style) but is honest about not handling complex fan-in/fan-out — worth naming that boundary rather than implying it scales to arbitrary DAGs.
A tenant edits a cron schedule for a job that's already sitting in the Redis warm buffer — how does that propagate?
The edit writes to the source-of-truth DB shard first. If using CDC, the change stream naturally emits an update event that overwrites (or removes and re-adds) the corresponding ZSET entry. If using a periodic sweeper instead of CDC, there's a real staleness window until the next sweep — worth flagging that gap explicitly and deciding whether the edit path should also directly patch Redis synchronously for that case, trading a bit of complexity for immediate consistency on edits specifically.
How do you test the timing wheel and lease logic without waiting real-time for jobs to come due?
Inject a mockable clock into the scheduler node rather than reading system time directly, so tests can advance time programmatically and assert the wheel fires the right bucket. For the lease race specifically, spin up concurrent threads hammering the same execution_id's claim and assert exactly one succeeds — the same property-test shape used to validate any NX-based distributed lock.
