Hotel Booking System

Search millions of date-range queries a day, but the design lives or dies on one hard invariant — never sell the same room-night twice. Date-range inventory, hold-then-pay flows with TTL leases, a read path that never trusts itself, and a channel manager that keeps Booking.com honest.

01

Requirements

Say these before drawing anything. The asymmetry is the story: reads are astronomically more frequent than writes, but the write path carries an invariant that reads never will — sum(sold) <= total for every room-night.

Functional

SearchFind hotels by city/dates/guests, filter by price, amenities, free cancellation
BookReserve a room type for a date range at a specific rate plan
PayHold the room, take payment, confirm; or pay-at-property
ManageCancel with policy-aware refunds, modify dates, view upcoming trips
DistributeSell the same inventory on OTAs (Booking, Expedia) without double-selling

Non-functional

Scale10⁷ searches/s peak, ~10³ bookings/s, ~500K hotels
CorrectnessNo oversells — the one non-negotiable
LatencySearch < 300ms p99; hold < 150ms p99
Availability99.9%; a failed booking is recoverable, a double-sell is not
ConsistencyInventory strongly consistent at book time; search may lag by seconds

The tension to name up front: this is two systems wearing one name. The read system (search, browse, price) wants caches, denormalization and eventual consistency everywhere; the write system (hold → confirm) wants a strongly consistent, serialized count on a single row per room-night. Every interesting decision follows from letting each side have what it wants, with the DB as the tiebreaker neither is allowed to skip.

02

End-to-End Architecture

Three lanes, deliberately separated by consistency requirement: search (eventual, cache-heavy), booking & inventory (strongly consistent, tiny blast radius), fulfillment & distribution (async, saga-driven).

search path (eventual) booking / inventory (strong) fulfillment & channels async / replication
Two rules make this diagram safe: (1) every read that leads to money — the checkout re-validation — lands on the DB, never a cache; (2) the only component allowed to decrement inventory is the Booking Service against its own shard. Redis holds and the channel manager both ask permission; neither takes it.
1

Search

Stateless Search Service answers from the Elastic index + fingerprinted Redis result cache. Availability shown here is explicitly best-effort — possibly seconds stale. Search never locks anything and never touches the inventory shards' write path.

2

Hold

Checkout re-validates against the authoritative per-room-night counts, then creates a TTL'd hold (15 min): a soft reservation that blocks others from overshooting the last rooms but is disposable — if the user vanishes, it evaporates and inventory snaps back.

3

Confirm

Payment succeeds (idempotency key = hold token), then a single atomic compare-and-swap on the DB converts the hold into a real booking row and permanent decrement — sold + 1 <= total enforced as a CHECK constraint. If the invariant fails, the user is told politely; the room was sold by someone else a millisecond earlier.

4

Fulfill

Booking events on Kafka fan out: notifications, the property's PMS, and the channel manager push updated availability to every OTA — each consumer idempotent, each retryable, none on the user's critical path.

03

Data Model

Everything hangs off one small fact table: room_type_inventory — one row per (room type × calendar date). The invariant lives in that table and nowhere else.

Catalog side

TableKey columns
hotelshotel_id PK, city, geo, amenities
room_typesroom_type_id PK, hotel_id FK, capacity
rate_plansrate_plan_id PK, room_type_id FK, refund policy, promo flags

A room type (Deluxe King) is sold in units (5 exist). Never model individual rooms for booking — you sell capacity counts, not keys; room assignment is a check-in-time concern for the property.

Inventory & transactions

TableKey columns
room_type_inventory(room_type_id, date) PK, total, sold, version
reservationsreservation_id PK, user_id, hotel_id, room_type_id, rate_plan_id, check_in, check_out, status
booking_holdshold_id (TTL'd, Redis + durable journal)

A 3-night stay decrements sold on exactly 3 inventory rows — one per night — in a single shard-local transaction.

The invariant, declared in the schema

CREATE TABLE room_type_inventory (
  room_type_id BIGINT       NOT NULL,
  stay_date    DATE         NOT NULL,
  total_rooms  INT          NOT NULL,
  sold_rooms   INT          NOT NULL DEFAULT 0,
  version      BIGINT       NOT NULL DEFAULT 0,
  PRIMARY KEY (room_type_id, stay_date),
  CONSTRAINT no_oversell CHECK (sold_rooms <= total_rooms)  -- the last line of defense
);

Versioning the three-table core (reservations ↔ room_type_inventory ↔ booking_holds) in one transaction is cheap because they all carry room_type_id-derived keys and co-locate on the same shard (section 08). Rate plans and prices are intentionally absent from the transactional path — a reservation snapshots the price it was booked at, so pricing changes never mutate history.

Why a per-night row and not one row per room-type: a single rooms_available counter can't answer "is tomorrow free?" once someone books only next month — availability is per-date, so the atomic unit must be per-date too. The flip side is that a stay spans N rows, which is exactly why shard-locality by room type (and never across hotels) is a design requirement rather than an optimization.

04

Availability & Concurrency — The Hard Part

Two users, one last room, same millisecond. Three credible patterns exist; the interview win is knowing the ordering between them and why the DB stays the final arbiter.

The date-range problem first

Half-open intervals [check_in, check_out) — a Tue→Thu stay occupies the Tue and Wed nights only. Modeling stays as date ranges invites off-by-one double-booking on turnover days; modeling them as sets of per-night rows makes overlap a point query on shared keys.

Pattern 1 — Pessimistic row lock

BEGIN;
SELECT * FROM room_type_inventory
  WHERE room_type_id = $1
    AND stay_date BETWEEN $2 AND $3
  ORDER BY stay_date      -- fixed lock order:
  FOR UPDATE              -- prevents deadlocks
-- app checks sold+1 <= total per row, then UPDATE … sold = sold + 1
COMMIT;

Simple, strictly correct, serializes all bookings of a room type through one row. Fine at hundreds of bookings/s per hotel — which is almost every hotel, almost always.

Pattern 2 — Optimistic version check (CAS)

UPDATE room_type_inventory
   SET sold_rooms = sold_rooms + 1,
       version    = version + 1
 WHERE room_type_id = $1 AND stay_date = $2
   AND sold_rooms < total_rooms          -- guard, not check
   AND version = $3;                     -- optional: retry signal
-- 0 rows affected ⇒ someone else won ⇒ re-read & retry or 409

No lock held across app round-trips; the sold < total guard plus the schema CHECK make oversell structurally impossible even if every other layer lies. Under high contention retries burn cycles — contention here means a hot hotel, which pattern 3 handles better.

Pattern 3 — Redis TTL holds in front of the DB (the two-phase answer)

The realistic failure mode isn't two concurrent updates — it's one user holding checkout for 8 minutes while a payment gateway hangs, blocking nobody but making the DB's "available" count a lie for everyone else. So the soft reservation moves to a store built for expiry:

-- Lua, atomic: count holds for room-type+night, refuse if it would exceed capacity
ZREMRANGEBYSCORE holds:{room_type_id}:{date} 0 now   -- sweep expired
local held = ZCARD holds:{room_type_id}:{date}
if held + (sold_from_db) < total then
  ZADD holds:{room_type_id}:{date} now+900 {hold_id}   -- score = expiry
  return OK  else return FULL
PropertyBehavior
What Redis guaranteesA soft reservation with a TTL — abandoned holds evaporate in ≤15 min with no sweeper logic to write
What Redis does NOT guaranteeDurability — a restart can forget holds. That's acceptable precisely because holds are not bookings; the truth is always the DB count
Confirm pathStill CASes sold_rooms in Postgres. Redis can over-reserve (crash + stale score); the DB can never oversell

Say the layering out loud: Redis decides who gets to try (fairness, queue-shaping, TTL expiry of abandoned checkouts); Postgres decides who actually gets the room (single-digit invariant). Losing Redis degrades UX — everyone falls through to CAS-and-retry — but never correctness. That is the same "disposable accelerators, authoritative ledger" split as the scheduler's Redis ZSET or the rider matcher's GeoSET, and naming that parallel scores points.

05

Booking Lifecycle — Hold → Pay → Confirm

The saga that makes "the user paid but has no room" and "the room is booked but nobody paid" both impossible.

Every arrow that crosses money has exactly one DB transaction behind it; every arrow that doesn't is allowed to be flaky and retried.
1

Hold (idempotent by design)

Checkout POST carries an Idempotency-Key. The service re-validates live DB counts, creates the Redis hold, and returns a signed hold token embedding (room_type, dates, price, expiry). Re-submitting the same key returns the same hold — double-clicks cannot double-hold.

2

Pay (money moves first, records follow)

Payment is captured against the gateway with the hold token as the idempotency key. A charge without a booking is a refundable anomaly; a booking without a charge is real lost revenue. So the order is always: auth succeeds → then confirm.

3

Confirm (the one true transaction)

One shard-local txn: CAS sold_rooms for every night, insert reservations row, mark hold consumed. If the CAS affects 0 rows — inventory vanished between hold and confirm (channel sold it, or a bug) — the txn aborts, gateway refund is queued as an event, user sees "just sold out, here's a comparable hotel." Rare, and graceful.

4

Reconcile the tails

A background reconciler sweeps the two scary corners: confirmed payments with no reservation (re-drive confirm, idempotent) and reservations whose hold token was never paid (shouldn't exist — alert). Event sourcing the saga states is overkill here; a status column plus these two sweeper queries covers it.

Pay-at-property is the same lifecycle minus step 2: confirm happens directly on hold+revalidate, and a no-show/cancellation fee is a separate later saga against a stored card token. Worth mentioning — interviewers like when a candidate notices that "guarantee with card" changes fulfillment, not the inventory protocol.

06

Search & Read Path

Reads outnumber writes by four orders of magnitude, so the read path is allowed to be wrong for seconds — with exactly one point where it must not be.

Fingerprint = hash of the fully normalized query (city, dates, guests, filters, page, currency, promo code). Same search, same answer — until TTL. The rank lives in Elastic; live per-night counts are appended from a short-TTL availability cache.

Why the index is not the truth, and that's fine

Elastic is fed by CDC from the catalog and inventory shards, so a sold-out hotel can appear available for a few seconds. The cost of that staleness is one disappointed user at hold time — the moment checkout begins, every displayed number is re-validated against the DB (section 05 step 1). "Eventual in the window shop, strong at the register" is the sentence to say.

The query shape that bites candidates

"Available for Tue–Thu" is a join across 3 date-partitioned keys — too expensive to compute per document at query time, so availability is precomputed per (room_type, date) into denormalized per-hotel calendar blobs refreshed by the CDC stream. At search time the service intersects the stay's dates against the candidate's blob — an in-memory filter over already-ranked top hits, not a DB join. Document staleness is bounded by the stream lag you monitor (_ingest_lag).

Pagination & de-dup: deep pagination over a changing result set is the classic trap — use search-after (tiebreaker on score + hotel_id) rather than from/size, and rank with a booking-value-aware score (conversion, margin, commission) — worth one sentence, interviewers rarely push past "why is this hotel first?".

07

Distribution & the Channel Manager

The same 5 Deluxe Kings are sold on your app, Booking.com, and Expedia. Each OTA has its own refresh cycle — which means your inventory count is a race with someone else's cache. This is where real-world overbooking actually comes from.

ARI = Availability/Rates/Inventory feed out; VCR = Room Variety/Reservation/Cashback protocol in. The channel manager is the only component permitted to mutate total_rooms allocations — OTAs never write inventory directly.

Allocation — the pattern that prevents OTA oversells

Instead of every channel selling against one raw count (and racing each other's caches), inventory is partitioned by channel: 5 Deluxe Kings ⇒ 2 direct, 2 Booking, 1 Expedia. A channel can only oversell its own allocation, and the allocation is re-balanced by the manager as VCR reservations land. Trade-off to name: allocations strand rooms (Booking is full while direct sits on 2 unused), so real systems pair allocation with a short buffer the manager re-alllocates every few minutes, and last-room sales go direct-only.

MitigationDetail
Push on change, not on scheduleEvery confirm/cancel emits an ARI update within seconds; scheduled full-refresh is the backstop, not the mechanism
VCR re-check before acceptWhen an OTA reservation arrives, validate against live DB counts before accepting; reject-with-sorry beats double-sell
Oversell policy, not just techIf a double-sell slips through anyway: "walk" the guest — rebook a same-or-better hotel nearby, pay the difference. The system should flag the conflict the instant it's detected; humans handle the guest
08

Sharding Strategy

One rule drives everything: a stay's N nightly rows and its reservation row must live on one shard, so the confirm transaction never spans shards.

DataShard keyWhy
room_type_inventoryhash(room_type_id)Every transactional query for a stay touches only its own room types; co-locates with the reservation's inventory rows. A hotel's room types spread across shards — fine, hotel-level ops are catalog, not transactions
reservationshash(user_id)"My trips" is the dominant read; shard-local. Hotel-side lookups (front-desk manifest) go through an async secondary index, not cross-shard scans
hotels / room_types / rate_plansunsharded or geo-replicatedSmall (10⁵–10⁶ rows), read-heavy, rarely mutated — replicate wholesale; the search index is already the read path

The hole to admit out loud

Sharding inventory by room_type_id and reservations by user_id means a booking's inventory rows and its reservation row can land on different shards — so either the confirm is a two-shard transaction (2PC or saga), or you give up one of the two colocatedities. The clean interview answer: store per-reservation nightly keys (room_type_id, date) denormalized onto the inventory shard with the reservation ID, and treat the reservation row's status as the user-facing truth written second, with the reconciler (section 05 step 4) closing any gap. Alternatives — shard both tables by hash(hotel_id) and index by user_id async — trade the hot-hotel problem back in; either is defensible if the cross-shard consequence is stated.

Hotels, not users, are the hot shard risk

A 1,500-room convention hotel on a concert weekend concentrates write load the way a hot tenant does in a scheduler — but within a single inventory shard. Because contention is per (room_type, date) row, the same CAS-and-retry that serves every other hotel degrades gracefully here; if it isn't enough, sub-partition that hotel's busiest room types across two logical shards with a routing table — same two-tier trick as the scheduler's hot-tenant mitigation.

Fault Tolerance & Edge Cases

Hold expires mid-payment TTL RACE

User's card authorizes at minute 15:04; their hold died at 15:00 and the last room was sold to someone else at 15:02.

MitigationConfirm's CAS is the arbiter: if it fails, auto-refund event fires, user gets a "sold out" page with rebooking options and the search for a comparable hotel prefilled. The hold TTL is a UX promise ("we'll try to keep it"), never a contract.

Double-sell from a channel cache INVARIANT BREACH

Booking.com's 5-minute-stale ARI let a guest book a room your app sold a minute ago — the CHECK constraint stops your DB, but their reservation still exists in the world.

MitigationAllocation (section 07) shrinks the blast radius to one channel's quota; VCR accept-time re-check stops most of the rest; the residual is an operational flow, not a code path — flag conflict, human "walks" one guest with rebooking + compensation. Design answer + policy answer together.

Confirm txn succeeds, response lost GHOST STATE

App retries the confirm POST — does the user get two bookings?

MitigationNo — confirm is keyed by the hold token; the retry replays the stored result of the first execution. Same idempotency machinery as the payment call, one layer up.

Timezone and turnover-day edge cases OFF-BY-ONE

"Tue→Thu" in a hotel that starts its night at 3am local vs a user booking from UTC. And cancellations at 23:59 in one timezone are next-day in another.

Mitigationstay_date is always the property-local calendar night — the hotel's timezone is part of the key's meaning, set once at catalog time. All TTLs and policy cutoffs computed in property-local time with the offset snapshotted on the reservation. Half-open [check_in, check_out) makes turnover-day (check-out morning) a non-event.

Redis failover wipes active holds SOFT-STATE LOSS

MitigationHolds are journaled to a durable append log (or Kafka) before being acknowledged, so a Redis rebuild replays live holds; even without that, users simply re-hold at next action — DB counts are untouched. Degraded UX, zero correctness impact: the point the whole holds-are-disposable design exists for.

Interview Playbook

Where exactly is the no-oversell guarantee enforced?
In one place: the Postgres UPDATE that increments sold_rooms with a sold_rooms < total_rooms WHERE-guard, backstopped by a table-level CHECK (sold_rooms <= total_rooms). Everything upstream — caches, holds, OTA feeds — is allowed to be wrong; if the DB says no, the answer is no. Naming the single enforcement point is more impressive than any amount of locking cleverness around it.
Why hold in Redis at all if the DB is the arbiter?
Because the DB's atomicity doesn't manage time: without holds, 70% of checkouts that stall on payment either block inventory behind a long transaction (pessimistic) or let sold-out hotels stay bookable for minutes (optimistic retry-storm). Redis holds shape the queue and expire themselves — the DB still decides. Say "holds are advisory, the CAS is authoritative" and the follow-up usually evaporates.
A user books 3 nights but one night's row fails the CAS — what happens?
Nothing, because the three nightly updates are one transaction: partial failure rolls the whole thing back and the user sees the sold-out flow. This is exactly why the sharding key must colocate a stay's nightly rows — cross-shard would turn an ordinary failure mode into a distributed-transaction question. The interviewer is testing whether you noticed that connection.
How does cancellation put inventory back?
The mirror transaction: decrement sold_rooms for each stay-night (guarded by sold_rooms > 0, same CHECK keeps it honest), flip the reservation status with a CAS so a concurrent no-show job can't double-release, and emit the same Kafka events so caches and ARI feeds refresh. Free-cancellation deadlines are policy evaluated against the property-local calendar, not the user's clock.
Search shows a hotel available, hold says sold out — how do you make that rare without killing throughput?
Tune staleness budget, not consistency: the availability hydrate cache gets a short TTL plus pub/sub invalidation on sell-out events, so most list pages are seconds-fresh; the fingerprint cache entry is dropped when its city's inventory churns. The honest framing: at 75% cache-hit and 1.2K QPS you cannot be perfectly fresh, so you make the known-sold-out cases vanish from search and push every residual lie to hold time, where it costs one apology, not a double-sell.
Why not model one row per room instead of capacity counts?
Guests buy a room type for a date range; which physical room fulfills it is decided at check-in by the property, and housekeeping/ maintenance/ room-assignment logic would all leak into your booking hot path. Capacity counts keep the invariant a single integer comparison; per-room rows multiply inventory volume, add a scarce-assignment step mid-checkout, and don't actually prevent oversells any better.
