01

Requirements

Scope it first: a platform that charges customers via external instruments (cards, UPI, wallets, net-banking), moves money to merchants, and can prove every rupee/dollar afterward. State the non-functional column before drawing — it is the whole design.

Functional

ChargeOne-time payments via card / UPI / wallet / net-banking, through PSPs and banks
Pre-authAuthorize now, capture later (or void) — hotels, fuel, rentals
RefundFull and partial refunds within the instrument's window
RecurringCard-on-file tokenized charges (subscriptions)
PayoutsSettle collected money to merchant bank accounts on schedule
StatementsPer-merchant transaction history + balance, exportable
DisputesChargeback intake, evidence submission, resolution posting

Non-functional

CorrectnessExactly-once money movement — never double-charge, never lose a completed payment
DurabilityEvery accepted intent survives crash; nothing silently dropped
ConsistencyBalances provably match transaction history (auditable to the cent)
Latency< 300 ms internal overhead; total gated by PSP (~2–5 s end-to-end)
Availability99.99% — a payment path outage is direct revenue loss per second
CompliancePCI DSS; card data must never enter scope; full audit trail
Idempotent retriesClients will retry blindly — the system must absorb it

The tension to name up front: you must deliver exactly-once effects on top of transports that are only at-least-once (client retries, network timeouts, PSP callbacks delivered 0..n times), and across systems you do not control — a PSP cannot enroll in your database transaction. Every hard decision below (idempotency keys, sagas, the ledger, reconciliation) exists to resolve that one sentence.

02

End-to-End Architecture

Five decoupled concerns: accept (idempotent payment API), execute (orchestrator talking to PSPs), record (append-only ledger), reconcile (bank files vs. our truth), and notify (async events + webhooks).

synchronous API path PSP execution ledger & events reconciliation

The pieces, and why each exists

Payments APIIdempotent front door; persists the intent durably before anything external happens
Idempotency storeUnique (merchant, key) → cached response; absorbs client retries (§05)
OrchestratorOwns the state machine, calls PSP adapters, resolves unknowns via get-status (§06)
PSP adaptersPer-provider plugins translating auth/capture/refund/get-status + verifying callbacks
LedgerDouble-entry postings appended once per confirmed state change (§07)
ReconciliationDaily bank settlement files matched against ledger; breaks to humans (§08)
NotifierConsumes events, fires HMAC-signed webhooks with their own retry ladder

Two golden rules

1 · Write the intent first. A payment request is persisted (with its idempotency key) before touching a PSP. If we crash next, the work is resumable — nothing external happened that we can't account for.

2 · Only real money is a settled fact from evidence. A payment is SUCCEEDED when the PSP says so on a response we read or a get-status query we ran or the bank file shows it — never because a callback "should have" arrived. The three-way redundancy (§06, §08, §11) is the design.

03

Data Model

Payments are not one table — the attempt, the PSP round, the money movement and the client retry are four different lifecycles that must never be conflated.

CREATE TABLE payment_intents (
  id            UUID PRIMARY KEY,
  merchant_id   UUID NOT NULL,
  order_ref     VARCHAR NOT NULL,          -- business reference
  amount_minor  BIGINT NOT NULL CHECK (amount_minor > 0),   -- always integer minor units!
  currency      CHAR(3) NOT NULL,
  method        VARCHAR NOT NULL,           -- card | upi | wallet | netbanking
  status        VARCHAR NOT NULL,           -- see state machine §04
  instrument_token VARCHAR,                 -- network/PSP token, NEVER a PAN (§10)
  failure_code  VARCHAR, failure_message VARCHAR,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ NOT NULL
);

CREATE TABLE payment_attempts (            -- one PSP round-trip each; retried flows add rows
  id           UUID PRIMARY KEY,
  intent_id    UUID NOT NULL REFERENCES payment_intents(id),
  psp          VARCHAR NOT NULL,
  psp_ref      VARCHAR,                     -- PSP's own transaction id (join key in §08)
  event_type   VARCHAR NOT NULL,            -- AUTH | CAPTURE | VOID | REFUND | GET_STATUS
  psp_status   VARCHAR NOT NULL,            -- SUCCESS | FAILED | UNKNOWN (timeout!)
  raw_response JSONB,                        -- redacted before storage (§14)
  created_at   TIMESTAMPTZ NOT NULL
);

CREATE TABLE idempotency_keys (
  merchant_id  UUID NOT NULL,
  key          VARCHAR NOT NULL,            -- client-supplied UUID
  request_hash CHAR(64) NOT NULL,           -- sha256 of semantic body fields (§05)
  response     JSONB,                        -- cached result for replays
  state        VARCHAR NOT NULL,            -- IN_PROGRESS | COMPLETED
  created_at   TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (merchant_id, key)           -- the constraint IS the feature
);

CREATE TABLE outbox_events (               -- transactional outbox (§11)
  id          BIGSERIAL PRIMARY KEY,
  aggregate   VARCHAR NOT NULL,             -- intent id → becomes Kafka partition key
  topic       VARCHAR NOT NULL,
  payload     JSONB NOT NULL,
  published   BOOLEAN NOT NULL DEFAULT false
);

Money representation — non-negotiables

Minor unitsStore amount_minor as integer (cents/paise) — never float, never decimal-through-arithmetic
Currency pinnedAmount without currency is a bug; FX happens only at settlement boundary (§08)
Immutable rowsCorrecting a mistake = new reversing entry, never UPDATE of an amount

Why separate attempts from intents

1 intent : N PSP roundsRetry after timeout, auth-then-capture, partial refunds — each is a distinct external transaction with its own psp_ref
The unknown trackerAn UNKNOWN attempt row is the durable to-do list for get-status resolution (§06)
Audit surfaceRaw responses + timestamps per round = the evidence trail disputes and audits run on
04

Payment Lifecycle & State Machine

Model it as a state machine whose arrows only fire on evidence. The classic split — authorize (hold funds) vs capture (take funds) — exists because shipping/hotels need reservations without taking money, and it's also what lets us keep "we asked" and "we have money" as provably different states.

                         ┌──────────┤ declined ├─► FAILED (terminal)
 CREATED ─► AUTH_PENDING ┤
                         └─► AUTHORIZED ─► CAPTURE_PENDING ─► CAPTURED ─► SETTLED
                              │  (hold)         (sweep)         (money)     (bank file §08)
                              ├─ expired / VOID ──────────────────────────► VOIDED
                              └─ capture failed ─► retry / FAILED
   CAPTURED ─► REFUND_PENDING ─► REFUNDED (full | partial, N attempts per refund)
   CAPTURED/SETTLED ─► DISPUTED (chargeback opened) ─► DISPUTED_WON | DISPUTED_LOST
StateMeaningFunds
CREATEDIntent durably persisted with idempotency keynone touched
AUTH_PENDINGPSP call in flight (or unknown — §06 owns this window)on hold at issuer if it lands
AUTHORIZEDIssuer placed a hold; PSP confirmed with psp_refreserved, not taken
CAPTUREDWe asked to take the money and PSP confirmedin flight to our merchant account
SETTLEDMoney actually arrived — proven by the bank file (§08)ours; merchant payout becomes due
FAILED / VOIDEDTerminal negative outcomes; void releases an auth holdnone

A charge, step by step (happy path)

1

Client POSTs with Idempotency-Key

Server inserts the (merchant, key) row — ON CONFLICT DO NOTHING. Conflict → return the cached/in-progress response, do zero new work (§05).

2

Intent + outbox in one DB transaction

payment_intents(CREATED→AUTH_PENDING) and the outbox_events row commit atomically — the event is guaranteed if the state is (§11).

3

Orchestrator calls the PSP adapter

auth(amount, currency, instrument, our_intent_id_as_reference). We send our ID as the PSP-side reference — the join key for callbacks, get-status and reconciliation.

4

Evidence lands → state advances

Success response (or verified callback, or get-status result) → AUTHORIZED, psp_ref recorded. A pending-only ledger posting is appended (§07).

5

Capture

Immediately (e-commerce) or on shipment (pre-auth flows) — same evidence rule. Capture confirmation → CAPTURED + real double-entry posting.

6

Settlement + notification

T+2 bank file confirms arrival → SETTLED. Kafka events drive receipts, merchant webhooks, dashboards, payout scheduling — all async, all idempotent consumers.

The 3 a.m. question: is PENDING a state you can act on? hazard

Never let the UI, the merchant, or a cron treat AUTH_PENDING as failed-then-recharge. Pending means "a PSP round exists that we haven't resolved with evidence." The only legal operations from pending are: resolve via get-status, or expire via the pending-timeout sweeper that queries before deciding (§06).

05

Idempotency — The Anti-Double-Charge Layer

Timeouts guarantee one thing: clients must retry, and some of those retries will duplicate a request that actually succeeded. Idempotency keys turn "at-least-once delivery" into "exactly-once effect" — it is the single most important mechanism in this design.

How the key flow works

# client side: one key per BUSINESS action, reused across retries of that action
POST /v1/payments
Idempotency-Key: 7f9c2e5a-…        # generated once when the user taps "Pay", then frozen
{ "order_ref": "ord_1042", "amount_minor": 49900, "currency": "USD", "method": "card" }
1

Claim

INSERT INTO idempotency_keys (merchant_id, key, request_hash, state='IN_PROGRESS') ON CONFLICT DO NOTHING. One and only one request ever wins this insert.

2

Loser path (conflict)

COMPLETED → replay the cached response (same status code + body). IN_PROGRESS → the first request is still executing: return 409 / or long-poll briefly — never start a second PSP call.

3

Winner path

Run the real flow; on terminal outcome, store the response and flip state to COMPLETED. Keys are retained ≥ the client's plausible retry window (24 h+) and swept after.

4

Misuse guard

Compare request_hash (canonical JSON of semantic fields only — not timestamps/nonce headers): same key + different body → 422 conflict. That catches "client reused a key for a different payment," which idempotency would otherwise silently honor as one and the same.

Scope of a key

Unique per (merchant_id, endpoint, key) — merchant A can never collide with merchant B, and a key on /payments must not match a later /refunds call. Keyed scope also keeps the store partitionable by merchant (§12).

Where the same pattern repeats

Idempotency is layered, not one point: API keys (§05) → PSP reference ID (auth deduped PSP-side), callback dedupe (psp_ref unique per event type, §11), webhook delivery (merchant acks + replay), ledger postings ((event_id, entry_type) unique, §07), payouts (batch ID at the bank). Every boundary crossing reuses the trick.

Interview nuance: idempotency keys protect one operation, not a business flow. "The user tapped Pay twice with two different keys" is two legitimate payments — deduping that is order-level (one PAID intent per order_ref unless explicitly re-authorized), a separate constraint worth stating out loud.

06

Timeouts, Retries & the Unknown-State Problem

The signature hard part of payments: when a PSP call times out, you don't know if the money moved. A timeout is not a failure — it's a third outcome, UNKNOWN, and it must be modeled as a first-class state with its own resolution machinery.

our PSP call ── outcome ∈ { SUCCESS,          retry never needed; advance state
                             FAILURE (code),   terminal or retry-with-new-attempt
                             UNKNOWN }         timeout / connection reset / 5xx pre-commit
Error classExamplesLegal action
Definitive declineinsufficient_funds, card_expired, do_not_honorMark FAILED; surface to user. Never blind-retry (decline codes are non-retryable; retry loops can trip issuer fraud rails)
Transient, pre-commit429/rate-limit, provider outage before the PSP processed anything (request rejected at edge)Retry same intent, exponential backoff + jitter — safe because PSP dedupes on our reference ID
UNKNOWN the hard oneread timeout, connection reset mid-request, 500 after processing startedNever re-POST a fresh auth. Query get-status(reference) until definitive; retry the same auth request only if the PSP's API is itself idempotent on reference

The resolution ladder for an UNKNOWN attempt

1

Poll get-status with backoff

Background resolver scans payment_attempts WHERE psp_status='UNKNOWN' (indexed), calls get_status(intent_ref) with exponential backoff — PSPs typically resolve within seconds to minutes.

2

Callback shortcut

If an async callback arrives first (§11), it satisfies the same evidence role — deduped and applied; the pending get-status find becomes a no-op.

3

Expiry policy (still evidence-based)

If no definitive answer after a bounded window: hold the intent in a user-visible "processing" state as long as the PSP's auth hold lifetime allows (issuer holds expire on their own clock anyway, usually 7 days, typically 1–3). Do not mark failed and let the user re-pay while a live auth exists.

4

The final arbiter: reconciliation

Anything still unknown at T+1 is adjudicated against the bank's settlement file: money arrived → force state to SETTLED with an audit note; nothing appears → VOID + close. The daily file is the ground truth we can't argue with (§08).

Fencing the PSP call itself

We send reference = intent_id (+ attempt_no) and PSPs dedupe on it: a re-issued identical auth returns the original result instead of creating a second charge. Combined with client idempotency keys, both ingress and egress are deduped — that's what makes the whole chain exactly-once in effect.

Orphan authorizations

The reverse ghost: PSP has an auth we lost track of (crash between call and write). Mitigations: write intent + IN_PROGRESS before the call (rule 1, §02); and a nightly sweep reconciling PSP-side open-authorizations list against our pending set, auto-voiding orphans. State this unprompted — it's the answer that separates SDE-2 from SDE-3.

07

The Double-Entry Ledger

Balances are not columns you UPDATE — they are projections of an append-only journal where every event posts ≥2 entries that always sum to zero. This is the component that makes the system auditable to the cent, and it is where interviewers test whether you've built money systems or only CRUD.

Account chart & posting rules

CREATE TABLE ledger_entries (
  id           BIGSERIAL PRIMARY KEY,
  journal_id   UUID NOT NULL,               -- one logical event groups its entries
  event_id     VARCHAR NOT NULL,            -- intent:CAPTURE, refund:REFUND:1 …
  account_id   UUID NOT NULL,               -- customer-payable, merchant-receivable, us-fees, us-settlement-bank …
  direction    VARCHAR NOT NULL CHECK (direction IN ('DEBIT','CREDIT')),
  amount_minor BIGINT NOT NULL CHECK (amount_minor > 0),
  currency     CHAR(3) NOT NULL,
  UNIQUE (event_id, account_id, direction)   ← replay-proof posting (§05 pattern, again)
);
CREATE INDEX ON ledger_entries (account_id, id);   -- balance sweeps stay shard-local
EventDEBITCREDIT
Auth succeeds (hold — memo only)no real entries; a pending memo keeps UX honest without touching money
Capture $100, fee $3see worked example belowzero-sum per journal, always

Read the journal like an accountant: every journal_id's entries sum to exactly zero — that invariant (SUM(debit) = SUM(credit) per journal, per currency) is continuously verified, and a violation pages someone.

A capture, posted (customer pays, we skim a fee, merchant is owed)

journal: intent_42:CAPTURE            $100 charge, 3% fee
  DEBIT   customer:payable              100      # customer owes money → liability settles
  CREDIT  us:settlement-pending         100      # money arriving via PSP is our asset-in-flight

journal: intent_42:SETTLED            # bank file proves arrival (§08)
  DEBIT   us:settlement-pending         100
  CREDIT  us:bank-account               100

journal: intent_42:FEE_SPLIT          # fee carved from what we owe the merchant
  DEBIT   us:bank-account               100
  CREDIT  merchant:receivable            97      # merchant is owed net-of-fee
  CREDIT  us:fee-income                   3      # zero-sum holds: 100 in = 97 owed + 3 earned

Every real-world movement — capture, settlement, fee carve, refund, chargeback, FX — is one or more zero-sum journals, appended once, keyed by event_id. Refund = the mirror journals in reverse; chargeback = a forced debit of merchant:receivable with a dispute-reference event.

Why not just UPDATE balance?

No audit trailA mutated number can't explain itself; regulators and merchants demand the sequence of events
Lost-update racesConcurrent debits on a hot row serialize on one lock — and silent double-spend bugs hide in retry paths
Unrecoverable errorsWith a journal you recompute the projection after any bug; with columns you reconstruct from bank files and prayer

Reading balances without melting the journal

Balance = SUM(entries) is too slow live, so maintain materialized balance snapshots per (account, journal-seq), updated in the same transaction as the append (single-shard ACID, §12) — i.e. the balance is a cache of a pure function, always re-buildable. Statement reads paginate the journal itself.

08

Settlement & Reconciliation

Between "PSP says captured" and "the money is in our bank and distributable" sits the async world of clearing. Reconciliation is the daily act of comparing their books to our books — it's not a reporting nicety, it's the system's final arbiter of truth (§06 step 4).

The pipeline

1

Ingest settlement files

T+1/T+2 batch files (or balance APIs) per PSP/bank: line items with psp_ref, gross, fees, FX rate, net. Idempotent import: (psp, file_date, line_hash) unique — re-delivered files must not double-post.

2

Match on the join keys

File line ↔ ledger journal via psp_ref (and our intent_id passed as reference, §04 step 3). Auto-match rate is the health metric — a good system runs >99.5%.

3

Classify breaks

File-only (money in, no journal → likely a lost/UNKNOWN payment → resolve state from evidence!), book-only (journal, no file → failed settlement, fee billing error, or still in-flight — recheck tomorrow's file), amount-mismatch (fee or FX delta → tolerance rules, e.g. ±1 minor unit auto-adjusts with an adjustment journal).

4

Post & age out

Every break becomes a work item with SLAs; money-affecting resolutions are themselves journals (adjustment entries always reference the break). Nothing is hand-edited.

Merchant payout = settlement downstream

payout_batch = Σ (merchant:receivable settled balances)   # only SETTLED money is payable
             − refunds/disputes owed back
             ≥ payout_floor?  schedule T+n (daily) else roll forward
   → freeze batch (snapshot the journal seq it covers) → bank transfer w/ batch-id reference
   → file confirms → DEBIT merchant:receivable / CREDIT us:bank-account journals

The batch references a journal sequence, so "what exactly comprises this payout" is answerable forever — that's what a merchant dispute about a payout reads on.

09

Refunds, Voids & Chargebacks

OperationAgainstMechanics & gotchas
VoidAUTHORIZED, not capturedRelease the hold; no money journals (none moved). Idempotent on intent; after capture, void is illegal — refund instead
RefundCAPTURED / SETTLEDNew intent child: refund_ref unique per PSP call; partial refunds tracked as running total (SUM(refunds) ≤ original enforced in the DB, not the UI). Window: instruments expire — a 2-year-old card may refund-to-original-fail → fallback to account credit/payout rail
ChargebackSETTLED (card networks)Initiated by issuer, not us — arrives via PSP notification: funds clawed back immediately (forced debit journal), response window 7–30 days to submit evidence, won/lost journals finalize. Clocks run on network time: SLA monitors must page before deadlines

Refund concurrency guard

Two simultaneous partial refunds can each pass a read-then-write check on the refunded total. Serialize per original intent: single-partition transaction (SELECT … FOR UPDATE on the intent row, or a compare-and-set on refunded_so_far) — the check and the posting live in one shard-local transaction (§12).

State the money-truth

A refund's lifecycle is the same machine in miniature: REFUND_PENDING → REFUNDED with the same UNKNOWN handling (get-status on refund_ref) and the same reconciliation (negative lines in the file). One pattern, applied recursively — say this explicitly; it shows the design is compositional, not a pile of special cases.

Tokens, 3DS & PSP Adapters

The card-data path decides your compliance surface. Design it so the PAN (raw card number) never touches our servers at all.

Tokenization & the vault

card form (PSP-hosted iframe / direct-to-PSP JS SDK)   # PAN goes client → PSP, bypassing us
        └─► PSP returns  network_token / vault_token    # only THIS reaches and is stored by us
Later recurring charge: POST /payments { instrument_token } → adapter → PSP vault → issuer
PCI scopeNever store/forward PANs → we drop from SAQ-D to a minimal SAQ class; CVV is never stored, ever
Network tokensIssuer-governed tokens that survive reissue/expiry (auto-updater) → higher recurring auth rates than vault PANs
Token vaultOur instrument_tokens table stores provider, token, BIN, last4, expiry — enough to render and route, nothing to steal

3DS / strong customer authentication (SCA)

An interleaved step in the state machine: AUTH_PENDING → CHALLENGE_REQUIRED (PSP returns redirect/JS challenge) → customer authenticates → PSP callback with the outcome → resume to AUTHORIZED or FAILED. Friction-free flows skip the challenge (risk-scored). Design consequences: the intent must survive the browser round-trip (state server-side, keyed by intent ID), and a challenge abandoned mid-way is just an expiring auth — resolved by the same ladder (§06), re-chargeable only after resolution.

The adapter seam (multi-PSP)

interface PaymentProvider {
  auth(intent)      capture(ref, amount)   void(ref)   refund(refund_ref, amount)
  get_status(psp_ref_or_intent_ref)        verify_callback(raw_http) → event | reject
}

Why an interface: PSPs differ on idempotency semantics, callback authenticity (HMAC vs mTLS vs IP allowlist), refund windows, and error-vocabulary. The orchestrator speaks only our state machine; adapters translate both ways (error-code mapping table per provider — including which map to UNKNOWN, which are terminal). Smart routing then picks a provider per transaction on cost / BIN-country / auth-rate, with automatic failover when one's health degrades — circuit breaker per adapter, and the same attempt lands on at most one provider until it's definitive-negative (double-submitting an auth to two PSPs "for redundancy" = double charge; name this trap).

11

Async: Outbox, Kafka & Webhooks

Everything downstream of a state change — receipts, dashboards, payout accruals, merchant webhooks — rides events. The two classic bugs are "lost event" and "duplicate event"; the outbox and consumer idempotency kill them respectively.

Transactional outbox (no lost events)

BEGIN;
  UPDATE payment_intents SET status='AUTHORIZED' …;   -- state change
  INSERT INTO outbox_events(aggregate, topic, payload)  -- same txn!
     VALUES ('intent_42', 'payment.authorized', …);
COMMIT;
-- relay process: poll/CDC → publish to Kafka → mark published

Publish-then-crash between DB commit and Kafka publish only delays delivery — the row is still unpublished. At-least-once to the bus, by construction.

Kafka plumbing (ties to the Kafka sheet)

Partition keyintent_id → per-payment ordering so consumers never see CAPTURED before AUTHORIZED
Topics by domainpayment.lifecycle, payout.batch, dispute.events, dlq.bad-callback
Consumer idempotencyEvery handler dedupes on event_id (processed-events table / unique upsert) — at-least-once consumption, exactly-once effect
RetentionCompacted topic for current intent state → replayable read models (§12)

Webhooks out to merchants — we are the unreliable party now

Merchants get push (webhook) + pull (status API) — push optimized for latency, pull is the merchant's own reconciliation tool. Delivery contract: retry ladder over hours (backoff), HMAC-signed body + delivery GUID so merchants dedupe our at-least-once; we log ack/non-ack per delivery, surface a "missed webhooks" replay UI, and never gate our state on their ack. Callbacks in from PSPs get symmetric treatment: verify authenticity before anything else, dedupe on (psp_ref, event_type), unknown/malformed → DLQ for humans, never a state change.

12

Scaling & Sharding

Two different workloads with two different keys. Payments API scales statelessly behind a load balancer; the hard part is the stateful side — intents, idempotency rows, ledger postings — where correctness demands transactions and hot accounts demand locality.

Shard keys — chosen so every transaction is shard-local

DataShard keyRationale
payment_intents + attempts + idempotency_keysmerchant_idThe charge txn (claim key + write intent + outbox) touches all three → same shard → single-node ACID, no distributed transaction
ledger_entriesaccount_idA posting touches the involved accounts; a journal spanning shards breaks the one-txn rule → see hot-account box
Statements / balancesaccount_idReads sweep one shard's index — shard-local pagination, no scatter-gather
Kafka lifecycle eventsintent_idPer-payment ordering (§11); independent of DB sharding

Hot accounts — the Amazon problem senior follow-up

One merchant = one shard, and during a sale the top merchant's shard absorbs a disproportionate share of traffic; every posting to merchant:receivable serializes on one row's balance lock. Answers, in escalating strength: (a) keep postings append-only and update the balance cache asynchronously in batches (balance reads lag by one flush interval — fine for statements, flag it); (b) sub-account splitting: each account is N logical sub-buckets, postings hash across them, balance = ΣN at read/cache time — same trick as splitting a hot counter key; (c) route top-N merchants to dedicated shards (explicit tiering, more ops burden). Name (b) as the default and be honest that per-account FIFO ordering gets weaker with it.

Read path (CQRS-lite)

Dashboards/receipts never hit the OLTP shards: lifecycle events build read models (search index for statement lookups, rollups for merchant dashboards) projected from Kafka — replayable from the compacted log, eventually consistent by design, with intent status API served from a replica for the "did my payment go through?" pull-path.

Multi-region note (state it, then scope it)

Route a merchant's entire flow (API → shards → orchestrator) to one region — payments are latency-tolerant enough that cross-region failover is DR (plan it, RPO≈0 via quorum log shipping), not geo-sharded live traffic. Data residency (EU cards stay in EU) can force region splits per jurisdiction.

AuditImmutable audit log of state transitions + who/what triggered each; dual-control (4-eyes) for any manual override tooling

Failure & chaos posture

PSP outage → circuit breaker opens, queue-and-retry non-urgent flows, user-visible "try later" for new auths, never auto-failover to a second PSP mid-attempt (§10 trap). DB failover → orchestrators drain; because UNKNOWN resolution is a durable sweeper, a restarted pod continues exactly where the crashed one stopped — the design has no in-memory critical state, and saying that out loud is worth points.

Interview Playbook

The questions you will actually get

How do you guarantee a customer is never charged twice?
Layered dedupe, each with a unique constraint: client idempotency key per business action (server-claimed via ON CONFLICT DO NOTHING, response cached for replay); our intent ID as PSP-side reference so a re-sent auth dedupes at the PSP; callbacks and get-status results deduped on (psp_ref, event_type); ledger postings unique on event_id. Timeouts go to UNKNOWN, never to "failed-and-recharge." Exactly-once effect, on at-least-once delivery.
The PSP call timed out. Walk me through your next three moves.
Record the attempt as UNKNOWN (durable, indexed). Backoff-poll get_status(reference) — any callback that arrives first serves as the same evidence. If still unresolved at the bounded window, hold the intent in "processing"; the T+1 bank file is the final arbiter: line present → SETTLED with audit note, absent → VOID. Never re-initiate a fresh charge from a pending auth.
Why double-entry instead of a balances table?
Auditability (every number explains itself as a journal sequence), invariants machines can check (SUM=0 per journal, per currency), and recoverability — a balance is a recomputable projection, so a bug is a backfill, not a forensic dead-end. Auth/capture/settlement also map 1:1 onto journals, which makes "when does money become spendable" a posting rule, not tribal knowledge.
The reconciliation file shows money for a payment we think failed. Now what?
File-only break → evidence outranks our state: re-query PSP for the ref (it will show AUTHORIZED/CAPTURED), force the intent's state via the audited transition path, post the missing journals from the file's own gross/fee/net, and file the break as resolved-with-cause. Then measure: if a class of these recurs (e.g. only on PSP B), the get-status ladder's window or mapping table is the bug.
How do you handle a 100× spike on the top merchant during a sale?
Shard skew is the failure mode: merchant-keyed shards and the account's posting row both go hot. Mitigations: sub-bucketed account balances (ΣN), append-only postings with batched balance-cache flushes, dedicated shard tier for top-N merchants, and stateless API scale-out — name the trade-off each introduces (balance staleness, weaker per-account FIFO) rather than claiming a free lunch.
When is the merchant's balance allowed to increase?
Only on SETTLED — proven by the bank file, not by a PSP "captured" response. PSP-says-captured is a receivable-in-flight; paying out on it means lending against unsettled clearing, which is how payment companies die. Say "pending ≠ payable" explicitly.
Design the refund API for concurrency: two partial refunds racing.
Enforce refunded_so_far + new ≤ original inside one transaction that takes a row lock on the original intent (shard-local, §12), with the refund's own idempotency key (refund_ref) so its PSP round gets the full UNKNOWN ladder too. Read-check-write across two transactions is the bug to point at.
Why is a webhook retry your problem and not the merchant's?
Because we're the party claiming "your payment succeeded" to an uncontrolled consumer: at-least-once with a backoff ladder, HMAC-signed bodies, a delivery GUID for their dedupe, delivery logs + a replay tool. But our state never depends on their ack — they always also have the pull API. Push for speed, pull for truth.

Cheat Sheet — One Pass Before the Interview

🔑 Correctness spine

  • Idempotency keys: claim → run → cache response; hash-mismatch = 422
  • Timeout = UNKNOWN, its own resolver ladder + bank-file arbiter
  • Intent persisted before any PSP call; state advances only on evidence
  • Auth ≠ capture ≠ settled — three states, three posting decisions

💰 Money spine

  • Integer minor units + pinned currency; corrections are new journals
  • Double-entry, zero-sum per journal, unique on event_id
  • Balance = cached projection, always recomputable
  • Payouts only from SETTLED; reconciliation runs the breaks queue

🏗️ Scale & ops spine

  • Shard by merchant_id (API state), account_id (ledger) — txn-local
  • Hot accounts → sub-buckets + batched balance flush
  • Outbox → Kafka (key=intent) → CQRS read models + webhooks
  • PCI scoped out by tokenization; verified callbacks; circuit-broken PSPs

The 60-second narration

"Clients retry, so the API is idempotent at (merchant, key) with a cached response. The intent is written durably before any PSP call, then a state machine — auth, capture, settle — advances only on evidence: a read response, a verified callback, or a get-status poll, because a timeout is UNKNOWN, not failure. Confirmed money movement posts zero-sum double-entry journals; balances are cached projections; merchants get paid only from what the bank's settlement file proves, and reconciliation is the final arbiter for everything still unresolved. Events flow through a transactional outbox onto Kafka, consumed idempotently; webhooks are our own at-least-once push with an HMAC and a replay tool. Sharding puts a payment's whole transaction on one shard by merchant, the ledger by account, with sub-bucketing for hot accounts — and the card PAN never enters our environment at all, because tokenization scoped the PCI away up front."
