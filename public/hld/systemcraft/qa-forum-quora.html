Designing a Q&A Forum (Quora / StackOverflow)

Simulate this design Draw it from memory

Difficulty: Intermediate Prerequisites:Caching, Database Indexing, and Fan-Out

TL;DR

A Q&A forum lets users post questions, write answers, and vote on both. Reads dominate writes 100:1, and most visitors arrive cold from a search engine to read one question and its top answers. The hard parts: serving that read volume cheaply, ranking answers so the best one lands first, and full-text search over 10M questions.

The shape of the answer: Postgres as the source of truth, Redis in front of the read path, Elasticsearch beside it for search, and rankings computed asynchronously rather than per request.💡 Elasticsearch is a search engine: it stores an inverted index, which maps each word to the documents containing it, so a keyword query is a lookup rather than a scan. Redis is an in-memory store used here purely as a cache. Learn more →

Understanding the Problem

A Q&A forum lets users post questions, write answers, and vote on both. Readers vastly outnumber writers — most traffic is people reading a question and its top answers, often arriving from a search engine. The hard parts: serving reads cheaply at scale (100:1 read-to-write ratio), ranking answers so the best one appears first, and providing full-text search across millions of questions.

The read-heavy skew is the single most important fact about this system. It means a cache is not an optimisation you add later — it is load-bearing from day one. It also means the write path can afford to be slower and do more work (recompute rankings, fan out to a search index) because writes are 1% of traffic.

Naive First Cut

New components:

  • Monolith API: One service handling everything - posting, reading, voting and searching - in the user’s request.
  • Single SQL DB: Questions, answers, votes and the search all in one database. Nothing is cached, so every page view is reassembled from scratch.

Why this breaks:

  • Hot questions (viral content) get 100K reads/sec — single DB can’t handle the load
  • Full-text search with LIKE '%keyword%' does a full table scan, no relevance ranking
  • Computing “top answers” on every read (sort by votes) is expensive when there are 500 answers
  • Feed generation for 10M users requires scanning all followed topics per request
  • No caching — same popular question page is recomputed on every request

The rest of the doc evolves this into a design that survives a front-page traffic spike.

Prior Art We’re Drawing From

  • Stack Overflow — famously runs on a remarkably small server footprint: a handful of SQL Server boxes plus aggressive caching, because an immutable-ish question page is close to a perfect cache candidate. Proof that read-heavy Q&A is a caching problem before it is a sharding problem. (Stack Overflow architecture)
  • Quora — separates the write store from the read/serving path and computes ranking and feed material asynchronously, keeping page loads free of ranking work. (Quora Engineering)
  • Reddit — its comment ranking uses time-decayed and confidence-based scoring (Wilson score for “best”) rather than raw vote counts, which is exactly the ranking problem in Deep Dive 2. (Reddit ranking algorithms)💡 Time decay means an older vote counts for less than a recent one. The Wilson score adds confidence: 8 upvotes out of 10 is a weaker signal than 800 out of 1000, even though the ratio is identical, and raw counts cannot tell the two apart.

Functional Requirements

Core (top 3)

  1. Post and read Q&A — users post questions, others write answers, anyone can read
  2. Vote on answers — upvote/downvote; answers ranked by score
  3. Search questions — full-text search across all questions by keyword and tags

Below the Line

  • User profiles, comments on answers, tag system, personalized feed, notifications, moderation tools

Non-Functional Requirements

  • Read latency — <100ms for question page loads (including top answers)
  • Scale — 10M questions, 50M answers, 100:1 read-to-write ratio
  • Search — full-text results in <200ms with relevance ranking
  • Availability — 99.9%; read path must stay up even if write path degrades

Below the Line

  • Strong consistency on vote counts (a vote appearing seconds late is fine)
  • Real-time updates to an open page
  • Multi-region active-active writes

Scale Estimation (Back-of-Envelope)

  • Corpus: 10M questions, 50M answers (~5 answers/question)
  • Read QPS (queries per second): ~50K question-page reads/sec average; a front-page item can add 100K/sec on one key💡 Back-of-envelope estimation is the rough arithmetic you do before choosing anything. Here it is used to argue a component *out of the design rather than in, which is the more valuable use of it. Learn more →*
  • Write QPS: ~500/sec combined (new questions, answers, votes) — 100:1 skew💡 “100K/sec on one key” is the phrase to notice. The total is survivable; the concentration is not, and Deep Dive 1 is entirely about what happens to that one key.
  • Storage: 50M answers × ~2KB ≈ 100GB of text, plus indexes. Fits comfortably in one Postgres instance with read replicas — this system does not need sharding, which is the main thing to say out loud.
  • Search index: 10M docs × ~1KB indexed fields ≈ 10GB, a small Elasticsearch cluster
  • Cache working set: the hot 1% of questions ≈ 100K pages × 50KB ≈ 5GB in Redis

The numbers matter because they tell you what not to build. 100GB and 500 writes/sec is a single-primary Postgres workload. Proposing a sharded multi-region datastore here is over-engineering, and a good interviewer will push back on it.

Core Entities

  • Question — title, body, tags, author, created_at, view_count
  • Answer — body, author, question reference, vote_score, created_at
  • Vote — user, target (answer/question), direction (up/down)
  • Tag — name, question count (for discovery)

High-Level Design

FR1: Post and Read Q&A

A question page is one question plus its answers, and the read-to-write ratio here is enormous — a question is written once and read for years. So this is a read-shaped problem.

New components we need:

  1. Q&A Service - owns questions and answers. Writes go to Postgres; reads assemble a question page.
  2. Postgres - questions and answers tables, the source of truth.
  3. Redis page cache - the assembled question page, keyed by question id with a short time to live (TTL). A question page is expensive to assemble and almost never changes, which is the textbook case for caching it.💡 A TTL is an expiry stamp on a cached entry: when it elapses the entry is deleted and the next reader has to rebuild it. Short TTLs keep data fresh; the cost of that choice is the whole of Deep Dive 1.

Flow:

  1. User opens a question → the service checks Redis for the assembled page
  2. Hit: return it. This is the overwhelming majority of reads
  3. Miss: read the question and its answers from Postgres, assemble, return
  4. Store the assembled page with a short TTL so the next reader is a hit

Why cache the assembled page rather than the rows? Because the expensive part is not fetching the rows, it is joining a question to its answers, its authors and their vote totals and rendering the result. Caching the finished page collapses all of that into one key lookup. Caching rows would still leave the assembly on every request.

What we have deliberately left broken. Reads are fast and the database is protected most of the time. The exception is the case that matters:

Nothing coordinates a cache miss. When a popular question’s entry expires — and TTLs expire on a timer, not on demand — every request in flight for it misses simultaneously and they all query Postgres for the same rows. The more popular the question, the more concurrent requests are waiting on that one expiry, so cache protection is weakest exactly when it is needed most. That is Deep Dive 1.

FR2: Vote on Answers

Voting is how the forum decides which answer is the good one, so a vote has to change both the stored score and what the next reader sees.

New components we need: none. A vote is a row and a counter, both in Postgres.

Flow:

  1. User upvotes an answer
  2. Insert a row into votes with a unique constraint on (user_id, answer_id), and increment the answer’s score. The constraint is what makes a double-click idempotent rather than two votes💡 Idempotent means doing the same thing twice has the same effect as doing it once. Here the database enforces it for free: the second insert for the same user and answer simply cannot exist, so no application code has to remember to check.
  3. Delete the cached question page so the next reader does not see the old ordering
  4. That reader misses, reassembles from Postgres, and sees the new score

How are answers ordered on the page? ORDER BY score DESC — the answer with the most net upvotes goes first.

Why store individual vote rows and not just a counter? Because a counter cannot answer “has this user already voted”, cannot be undone when they change their mind, and gives no way to detect a brigade after the fact. The counter is a denormalised convenience; the rows are the record.

What we have deliberately left broken. Votes are recorded, idempotent per user, and visible immediately. The ordering they produce is the problem.

ORDER BY score DESC ranks by lifetime accumulated votes, which is a measure of how long an answer has existed at least as much as how good it is. An answer posted in 2015 with 400 votes sits permanently above a better answer posted last month with 40, and because position on the page drives the votes, the top answer keeps earning votes because it is on top. The ranking is self-reinforcing, so the one thing it cannot do is let a better answer overtake a worse one. That is Deep Dive 2.

FR3: Search Questions

People arrive looking for a question that already exists. The titles and bodies are already in Postgres, so query them.

New components we need: none. The text is in columns we already have.

Flow:

  1. User types “distributed caching” into the search box
  2. The service runs SELECT ... WHERE title LIKE '%distributed caching%' OR body LIKE '%distributed caching%'
  3. Return the matching rows, most recent first

Why start here rather than reaching straight for a search engine? Because it is one query against data we already store, it needs no second system to keep in sync, and for a forum with a few thousand questions it is genuinely the right answer. The reason to replace it is specific and measurable rather than aesthetic, and naming that reason is the point of the deep dive.

What we have deliberately left broken. This finds questions, and it fails in two distinct ways at 10M questions:

  • A leading-wildcard LIKE cannot use an index. '%phrase%' means the match can start anywhere in the column, and a B-tree can only seek on a known prefix — so this is a full scan of 10M rows per search, with a substring comparison on every title and body.💡 A B-tree index is a sorted tree, so it can jump straight to entries beginning with “distr”. It has no way to find entries containing “distr” somewhere in the middle, which is why a leading wildcard turns the index off entirely.
  • There is no notion of relevance. Step 3 orders by date because that is the only signal available. A question that merely mentions the phrase in passing outranks the canonical answer to it, and a search for “caching” cannot match “caches” or “cached” at all, because a substring comparison has no concept of word stems or of which words matter.

Both are Deep Dive 3.

Why Postgres instead of sharding? 10M questions × 50M answers × ~2KB ≈ 100GB of text. That fits comfortably in one Postgres instance with read replicas. Stack Overflow runs on a similar footprint. Sharding adds complexity that this read-heavy, moderate-write system doesn’t need.

Data Modeling

Postgres (Primary DB — questions, answers, votes):

CREATE TABLE questions (
    question_id UUID PRIMARY KEY,
    author_id UUID NOT NULL,
    title VARCHAR(300) NOT NULL,
    body TEXT NOT NULL,
    tags VARCHAR(50)[] NOT NULL,
    view_count INTEGER DEFAULT 0,
    vote_score INTEGER DEFAULT 0,
    answer_count INTEGER DEFAULT 0,
    accepted_answer_id UUID,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);
CREATE INDEX idx_questions_tags ON questions USING GIN(tags);
CREATE INDEX idx_questions_score ON questions(vote_score DESC);

CREATE TABLE answers (
    answer_id UUID PRIMARY KEY,
    question_id UUID NOT NULL REFERENCES questions(question_id),
    author_id UUID NOT NULL,
    body TEXT NOT NULL,
    vote_score INTEGER DEFAULT 0,
    is_accepted BOOLEAN DEFAULT false,
    created_at TIMESTAMP NOT NULL
);
CREATE INDEX idx_answers_question ON answers(question_id, vote_score DESC);

CREATE TABLE votes (
    user_id UUID NOT NULL,
    target_id UUID NOT NULL,  -- question_id or answer_id
    target_type VARCHAR(10) NOT NULL,  -- QUESTION or ANSWER
    direction SMALLINT NOT NULL,  -- +1 or -1
    created_at TIMESTAMP NOT NULL,
    PRIMARY KEY (user_id, target_id)
);

How Vote Score Updates Propagate:

  1. User upvotes an answer → INSERT INTO votes (user_id, target_id, 'ANSWER', +1) — unique constraint prevents double-voting
  2. UPDATE answers SET vote_score = vote_score + 1 WHERE answer_id = ? — atomic increment
  3. Publish VOTE_CAST event to Kafka → cache invalidation worker DELetes question:{qId} and answers:{qId}:top from Redis
  4. Elasticsearch is updated async (Kafka consumer) — search results reflect new score within seconds💡 “Async” here means the user’s vote returns as soon as Postgres has it, and the search index catches up a second or two later. The alternative - writing to both stores inside the request - makes the vote as slow and as fragile as the slower store.
  5. Next page load rebuilds cache from Postgres (read-through pattern)

Deep Dives

1) A question goes viral and its cache entry expires. Why does the database fall over?

Problem: FR1’s cache protects Postgres by serving the assembled page, and nothing coordinates what happens at the moment that page expires.

Bad: the plain TTL cache FR1 built. A question goes viral and 100K users are on it simultaneously. The TTL fires — on a timer, with no regard for how many people are reading — and all 100K requests miss at once, then all 100K query Postgres for the same question and the same answers.💡 This failure has a name: a cache stampede, or thundering herd. The load is not high because the day is busy; it is high because one moment of expiry converts a steady stream of cache hits into a single simultaneous burst on the store behind it.

The database is not asked for 100K different things, which it might survive. It is asked for one identical thing 100K times inside a few milliseconds, and it has to assemble every one of those answers independently because none of them can see the others. Connections saturate, the pool queues, and requests for unrelated questions start timing out too — so one viral question degrades the whole forum.

The property that makes this nasty is the inversion: cache protection is proportional to hit rate, and at the moment of expiry the hit rate for the hottest key is zero. The more popular a question is, the more certain it is to take the database down when its entry lapses. It also does not show up in testing, because at low traffic the expiry window closes before a second request arrives. and the whole site slows down.

Use a cache-aside pattern with a short TTL (30s). On cache miss, only one request fetches from DB (using a or single-flight pattern). All other concurrent requests wait and receive the cached result once the first one completes.

For known hot content (trending questions, front-page posts), use a “cache warming” strategy. A background job identifies trending questions (by view velocity) and proactively refreshes their cache before TTL expiry. This eliminates cache misses entirely for the hottest content. Combined with on Postgres for the long-tail of unpopular questions, the primary DB only handles writes.

2) The best answer was posted last month and nobody will ever see it. Why?

Problem: FR2 orders answers by score DESC. Score is a lifetime total, so it measures accumulated exposure as much as quality.

Bad: ORDER BY score DESC, exactly as FR2 built it. An answer from 2015 with 400 votes outranks a better answer from last month with 40, and it will continue to do so for years, because 400 > 40 regardless of which one is correct today.

The mechanism is a feedback loop, and that is what makes it unfixable by waiting. Position drives visibility, visibility drives votes, so the answer at the top accrues votes because it is at the top. A newer answer has to overcome a deficit that is actively growing while it sits below the fold. The ranking does not slowly converge on the better answer; it converges on whichever answer got there first.

This matters more here than on most ranked lists because the content goes stale in a specific way: the 2015 answer may have been right about a library version that no longer exists. So the system reliably surfaces the most-voted answer and that is often the obsolete one, with the correction buried underneath it.

Combine vote score with engagement signals: answer acceptance (by the question author), view-time (do readers scroll past it or stop?), and author reputation. Weight these into a composite ranking score. Compute rankings (not on every page load) and cache the sorted result. Re-rank every few minutes or on significant vote changes (>5 new votes). This keeps page loads fast while providing meaningful rankings.

3) A leading wildcard cannot use an index. How do we search 10M questions by relevance?

Problem: FR3 searches with LIKE '%phrase%'. That is a substring test, and search is not a substring problem — which shows up as both a performance failure and a quality failure.

Bad: the LIKE '%distributed caching%' FR3 built. Two independent defects.

No index can serve it. A B-tree can seek to a known prefix; a leading wildcard says the match may begin at any character, so there is nothing to seek to. Every search is a full scan of 10M rows with a substring comparison per title and body. At any real query rate that is the whole database doing one user’s work.

It has no idea what relevance means. A substring test is boolean — a row either contains those characters or it does not — so there is no score to order by and FR3 falls back to date. Three consequences: a question mentioning the phrase once in a comment ranks equal to the canonical thread about it; “caching” does not match “caches” or “cached”, because stemming requires knowing the text is language rather than bytes; and multi-word queries cannot prefer rows where the words appear together over rows where they appear in unrelated paragraphs.

The second defect is the one that justifies a second system. The performance problem has cheaper partial answers — a trigram index can make substring matching indexable — but none of them produce a ranking, and a search box without relevance is not search.💡 A trigram index chops every string into overlapping three-character pieces and indexes those, so “caching” can be found from the middle of a column. Stemming, which it still does not give you, is the step that reduces “caches” and “cached” to one root word so a search for either finds both.

Elasticsearch index with standard BM25 scoring. Questions are indexed by title, body, and tags. Search returns results ranked by text relevance. Sync from Postgres to Elasticsearch via Kafka (a , or CDC, pipeline) with <10s lag.

Boost search relevance with engagement signals. Weight title matches higher than body matches. Boost questions with more views, votes, and accepted answers. Add tag-based filtering (faceted search). For “unanswered” queries, filter to questions with zero accepted answers — useful for contributors looking to help. Combined with search-as-you-type (prefix completion on the title field), users find answers before even finishing their question.

Design Self-Audit

Question Answer
Do we need sharding? No. ~100GB and ~500 writes/sec fits one Postgres primary. Scale reads with replicas and Redis. Say this explicitly — resisting unnecessary sharding is a signal, not a gap.
Redis goes down? Reads fall through to Postgres read replicas. Latency rises and the primary must be shielded by single-flight, but the site stays up. This is why the cache sits in front of replicas, not the primary.
Elasticsearch goes down? Search degrades to a Postgres full-text query (tsvector) with worse relevance, or returns “search temporarily unavailable.” Browsing and reading are unaffected — search is a separate failure domain.
Stale vote counts? Acceptable. A vote landing in the cached page seconds late costs nothing. We invalidate on write and accept a short window of staleness.
Cache invalidation on every vote? On a viral question that means constant invalidation, defeating the cache. Fix: don’t invalidate on every vote — let the short TTL expire naturally, and only invalidate on answer add/edit. Vote counts are the one field allowed to be slightly stale.
Vote fraud? Unique constraint on (user_id, target_id) makes double-voting impossible at the DB level. Ring-voting detection is an offline analytics job, not a request-path concern.

💡 A tsvector is Postgres’s parsed form of a text column - the list of normalised, stemmed words in it - which Postgres can index and score. It is real full-text search, just less capable than a dedicated engine, which is exactly what you want from a fallback.

Final Architecture

New components: five boxes appear here that the functional requirements never had.

  • CDN: an edge cache in front of everything. A logged-out question page is byte-identical for every visitor, and most traffic is logged-out, so the cheapest request is the one that never reaches us at all.
  • Replicas: read-only copies of the Postgres primary. Cache misses land here rather than on the primary, so a read surge can never starve writes.
  • Kafka (changes): carries the database’s change stream. It exists so that one write produces one event with two independent consumers, instead of the write path having to call them both.
  • Elasticsearch: the search index from Deep Dive 3, kept in sync from that stream.
  • Ranking Worker: recomputes time-decayed answer order from Deep Dive 2 and writes the pre-sorted list into Redis, so a page load never sorts 500 answers.

How it works end-to-end (read path — 99% of traffic):

  1. User requests a question page — usually arriving from a search engine, so the request is cold for that user but hot for the system
  2. CDN serves anonymous traffic — logged-out page views are identical for everyone, so they can be cached at the edge outright
  3. Redis page cache — on CDN miss, the assembled page (question + ranked answers) is looked up by question ID
  4. Read replicas absorb misses — a cache miss reads from a replica, never the primary, so read traffic can never starve writes

How it works end-to-end (write path — 1% of traffic):

  1. Writes go to the Postgres primary — questions, answers, and votes, with a unique constraint on votes preventing double-counting
  2. CDC stream publishes changes to Kafka — one change feed, two consumers, so neither indexing nor ranking sits in the user’s request
  3. Elasticsearch stays in sync — the indexer consumes the stream and updates the search index within seconds
  4. Ranking Worker recomputes answer order — time-decayed scores are computed off the request path and written back to Redis as a pre-sorted list, so page loads never sort 500 answers

Key Technologies

Term What it is
Read Replica A streaming copy of the primary DB that serves reads only. The lever for a 100:1 read skew — add replicas, not shards.
Single-flight (request coalescing) On a cache miss, only one request fetches from the DB while the rest wait for its result. Prevents a thundering herd on viral content.
CDC (Change Data Capture) Streams a database’s commit log as events. Keeps Elasticsearch in sync without dual-writes, which would risk divergence.
BM25 Elasticsearch’s default relevance scoring — term frequency weighted by how rare the term is across the corpus.
Wilson score / time decay Ranking formulas that account for vote confidence and recency, so a new good answer can outrank an old popular one.

What’s Expected at Each Level

Level Expectations
Mid Redis cache for read-heavy pages. Elasticsearch for full-text search. Basic vote-sorted answers. Explain read/write ratio implications.
Senior Thundering herd protection (single-flight). CDC pipeline to sync ES. Time-decayed ranking formula. Read replicas for the long tail.
Staff+ Cache warming for trending content. Composite ranking with engagement signals. Faceted search with boost tuning. Feed generation strategy for followed topics.

🎯 Key Takeaways

  • A 100:1 read skew makes the cache load-bearing, not an optimisation — design the read path first
  • Don’t shard this system. 100GB and 500 writes/sec is one Postgres primary plus read replicas; proposing shards is the classic over-engineering trap here
  • Rank asynchronously, serve pre-sorted. Sorting 500 answers per page load is the mistake; compute scores on a worker and cache the ordering
  • Raw vote counts are a bad ranking. Time decay lets fresh, better answers surface past entrenched old ones
  • Search is a separate failure domain — Elasticsearch going down should degrade search, not take down reading
  • Invalidate on answer changes, expire votes by TTL — invalidating on every vote destroys the cache exactly when you need it most
