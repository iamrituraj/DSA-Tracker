The module is a flat collection of independent ES-module (.mjs) CLI scripts with no shared library — each script is self-contained and reads/writes files under `data/` and `public/data/`. Two families coexist: (1) data-pipeline scripts (`prepare-data.mjs`, `extract-tuf-links.mjs`, `java-to-csharp.mjs`) that transform source inputs — `data/problems.raw.json` plus an offline HTML dump at `/private/tmp/tuf-a2z.html` — into curated outputs (`problems.json`, `topics.json`, `patterns.json`, `tuf-links.json`) using regex-based normalization and declarative rule tables; (2) batch-solution scripts (`batch1.mjs` … `batch13.mjs`) which export plain objects mapping problem IDs to approach entries containing Java and C# code, consumed by `merge-batch.mjs` (merges verified batches into `public/data/solutions.json` in catalog order), `verify-batch.mjs` (schema validation against `problems.json` plus best-effort `javac` compilation using shared node-type stubs from `_stubs.mjs`), and `verify-lld*.mjs` / `ftest*.mjs` for linked-list and functional tests. Dependency direction is strictly one-way: scripts read from the repo's data tree and write back; there are no cross-imports between batch modules, and only `verify-batch.mjs` imports the shared `_stubs.mjs` helper.
