## What system/approach is used

The application has no dedicated configuration framework or config file format (no `.env`, `config/`, YAML, TOML). Instead, runtime configuration is loaded entirely from **Node.js process environment variables** at the serverless API layer and from **static JSON files** served by Vite for the browser. The frontend stores user preferences in `localStorage` under keys like `dsa-progress`, `dsa-notes`, `dsa-solutions`, `dsa-activity`, and `dsa-settings`.

## Key files and packages

- `api/_session.js` — session cookie signing; reads `SESSION_SECRET` and detects deployment via `process.env.VERCEL` to toggle the `Secure` cookie flag.
- `api/auth.js` — password-based authentication; reads `APP_ACCESS_PASSWORD` from the environment and uses a timing-safe comparison against the request body password.
- `api/state.js` — cloud persistence endpoint; requires `DATABASE_URL` to connect to Neon (`@neondatabase/serverless`) and creates/queries the `dsa_tracker_state` table.
- `src/main.jsx` — client-side entry; hardcodes static data URLs (`/data/problems.json`, `/data/solutions.json`, `/data/tuf-links.json`) and persists all user state to `localStorage`.
- `package.json` — declares only runtime dependencies (`react`, `vite`, `@neondatabase/serverless`, `lucide-react`); build/dev scripts are the only place where tooling configuration lives.
- `public/data/*.json` and `data/*.json` — static datasets consumed by the UI (problems, topics, patterns, solutions, TUF links).

## Architecture and conventions

1. **Serverless API-only configuration**: All secrets and service endpoints live exclusively in environment variables on the hosting platform (Vercel). There is no local `.env` file checked into source control. The three required variables are:
   - `SESSION_SECRET` — HMAC key for signed session cookies (throws if missing).
   - `APP_ACCESS_PASSWORD` — single shared password for logging into cloud sync.
   - `DATABASE_URL` — Neon connection string; without it the state endpoint returns a 500 error.
2. **Deployment-aware behavior**: `api/_session.js` checks `process.env.VERCEL` to conditionally set the `Secure` flag on cookies, so the same code runs both locally (insecure) and on Vercel (secure).
3. **Static data as configuration**: Problem catalog, topic taxonomy, solution approaches, and TakeUForward editorial links are baked into JSON files under `public/data/`. The React app fetches them at startup via relative paths — they are treated as immutable configuration rather than runtime data.
4. **User settings vs. app configuration**: User-facing settings (`dailyGoal`, `theme`) are stored per-browser in `localStorage` under `dsa-settings` and merged with any cloud-synced settings. App-level configuration (secrets, DB URL, passwords) is never exposed to the browser.
5. **No feature flags or config toggles**: Behavior is controlled solely by whether the required environment variables are present. Missing `DATABASE_URL` disables cloud sync; missing `SESSION_SECRET` or `APP_ACCESS_PASSWORD` breaks auth.

## Conventions and constraints

- Secrets must be provided as environment variables on the deployment platform; the code explicitly throws or returns errors when `SESSION_SECRET`, `APP_ACCESS_PASSWORD`, or `DATABASE_URL` are absent.
- Cookie security adapts automatically based on the presence of `process.env.VERCEL`; developers should not add their own `Secure` flag.
- Static data files under `public/data/` are the single source of truth for problem metadata and are fetched at app load — they must be kept in sync with the curated copies under `data/` that are generated by scripts in `scripts/`.
- All user state is keyed by problem `id` and persisted in separate `localStorage` entries; there is no schema migration or versioning for these keys beyond the export/import backup format (which includes a `version: 3` field).
- The backend does not read any config files at startup; configuration is evaluated lazily per request, which means misconfiguration surfaces as an HTTP error response rather than a startup failure.
