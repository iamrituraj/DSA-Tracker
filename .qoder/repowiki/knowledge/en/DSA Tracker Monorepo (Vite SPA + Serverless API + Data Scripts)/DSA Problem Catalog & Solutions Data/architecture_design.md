The module is a flat collection of static JSON assets split into two locations with different audiences. `data/` holds the canonical source-of-truth used by build/tooling: `problems.json` (a ~4k-entry array of problem records keyed by `id`, each carrying `title`, `topic`, `pattern`, `difficulty`, `status`, `url`, `videoUrl`), `patterns.json` (topic-to-pattern-name mapping), `topics.json` (flat list of top-level topics), and `problems.raw.json` (likely an intermediate/raw dump). `public/data/` holds the browser-consumable subset: the same `problems.json`, `patterns.json`, `topics.json` plus `solutions.json` (a `{problemId -> {approaches:[...]}}` map where each approach stores `id`, `title`, `level`, `time`, `space`, `explanation`, and multi-language `code` blocks) and `tuf-links.json` (a `{problemId -> takeuforward URL}` lookup). There is no runtime code in this scope — consumers read these files directly as data, so the dependency direction is one-way: application code depends on these JSON schemas without importing them at build time.
